# Research: Vendor OSCAL/FedRAMP Files Instead of Submodules

| # | Decision | Rationale | Alternatives considered |
|---|----------|-----------|--------------------------|
| R1 | Keep the existing `third_party/oscal`, `third_party/oscal-content`, `third_party/fedramp-automation` directory names and preserve each vendored file's upstream-relative subpath (e.g. `third_party/oscal-content/nist.gov/CSF/v2.0/json/...`). | `source_repo`/`source_path` in the existing `tests/fixtures/golden-oscal/**/*.provenance.yaml` sidecars, and the path references in `data-model.md`/`plan.md`/`research.md` (R8) of `001-oscal-ai-conversion`, already read `third_party/oscal-content` and `third_party/fedramp-automation` as plain paths — preserving them means those references stay correct without a rename, honouring Principle XI (edit only what actually changed). | Flatten or rename the vendored directories — rejected: would force editing every existing path reference above for no behavioural benefit. |
| R2 | Each vendored set gets its own `third_party/<name>/PROVENANCE.md` (upstream repo URL, commit SHA, retrieval date, license), colocated with the files it describes. | Mirrors the sidecar-provenance convention ADR-0030's 2026-09-28 implementation note already established for `tests/fixtures/golden-oscal/**/*.provenance.yaml`, so the repo has one consistent provenance pattern. Co-location also survives a partial copy or grep better than one shared record. | A single provenance table in `third_party/README.md` covering all three sets — rejected: `third_party/README.md` already carries per-vendor narrative; a separate file next to each vendored set is more durable and greppable. |
| R3 | Golden-fixture `*.provenance.yaml` `source_repo`/`source_path` fields need **verification, not rewriting**: because R1 preserves existing paths, these fields already point at the (now vendored-not-submodule) location. | Confirms spec FR-008 is satisfied by checking each field still resolves correctly post-migration, rather than assuming every field must change value — avoids a needless mechanical edit pass that would touch 13 files for no reason. | Rewrite every `source_repo` value regardless — rejected: would be a no-op edit wherever R1's path is unchanged, and risks introducing a typo in an otherwise-correct field. |
| R4 | Record the submodule → selective-file-vendoring switch as a new dated "Implementation note" appended to **ADR-0030** (which already decided how these three sources are vendored), not a new ADR. | ADR-0030 is already structured as a running decision record with dated implementation notes (2026-09-20, 2026-09-24, 2026-09-28) for exactly this kind of follow-on change to the same decision; a new ADR would fragment one decision across two files, against Principle X. | A new ADR superseding ADR-0030 — rejected: the decision area (how to vendor `oscal`/`oscal-content`/`fedramp-automation`) is unchanged; only the *mechanism* (submodule vs. selective files) changes, which is what ADR-0030's existing implementation-note pattern is for. |
| R5 | Each vendored set also retains a copy of its upstream `LICENSE`/`LICENSE.md` file alongside the vendored content. | `wiki/oscal-compliance.md` and `third_party/README.md` already cite `third_party/oscal-content/LICENSE.md` and `third_party/fedramp-automation/LICENSE.md` directly as the basis for the public-domain/CC0 license claims; dropping them on vendoring would silently break that citation trail and weaken the license-compliance rationale GH #167 itself relies on (avoiding `fedramp-automation`'s non-CC0 Go dependency surface while keeping its own CC0 core auditable). | Summarize the license in `PROVENANCE.md` only — rejected: a paraphrase is not the same as the upstream's own license text as a citable artefact. |
| R6 | Wiki pages citing the old decision (`wiki/oscal-compliance.md`, `wiki/architecture.md`, `wiki/controls-compliance-catalog.md`, `wiki/index.md`) are regenerated via the `wiki-librarian` skill after ADR-0030 and `third_party/README.md` land, never hand-edited. | The constitution lists `wiki/` as "Derived — never a source"; hand-editing would drift from the sources `wiki-librarian` resynthesizes from. | Hand-edit the four wiki pages directly — rejected: violates the constitution's derived-content rule. |
| R7 | Submodule removal is mechanical git surgery: `git submodule deinit` the three paths, `git rm --cached` their gitlinks, delete their `.gitmodules` stanzas, remove the matching `.git/modules/<name>` entries, then add the selected files as ordinary tracked files. On this devcontainer's drvfs-mounted workspace, the `.git/modules` cleanup needs `sudo` (chmod-on-write EPERM, per AGENTS.md's documented quirk). | Standard, reversible-if-caught-early git submodule removal sequence; calling out the `sudo` need up front avoids rediscovering the drvfs quirk mid-task. | Leave the old gitlink/`.gitmodules` entries in place and overlay files on top — rejected: leaves a broken, dangling submodule registration that `git submodule update --init` would still try (and fail) to resolve. |
| R8 | The set of files to vendor is exactly what GH #167 names: the NIST OSCAL schema files; the SP 800-53 rev5 catalog plus its LOW/MODERATE/HIGH/PRIVACY baseline profiles; the FedRAMP LOW/MODERATE/HIGH resolved baseline catalogs under `GoComply/fedramp`'s `bundled/catalogs/` (no PRIVACY baseline exists upstream). | The issue explicitly defers "which exact files beyond the ones listed" as separate, still-open follow-up work — scoping this feature to exactly the named files keeps it independently shippable and avoids speculative vendoring. | Audit all current readers of `third_party/{oscal,oscal-content,fedramp-automation}` now to find every file actually touched — rejected: explicitly out of scope per the issue; tracked as its own follow-up. |
| R9 | No CI workflow change is needed: `.github/workflows/ci.yml`'s `submodules: true` checkout option stays, since it still must initialize the one remaining submodule (`it4it`). | Confirmed by inspection — the only two `submodule` references in `.github/workflows/` are the generic `submodules: true` checkout flag, not something naming the three removed submodules individually. | Make the checkout step conditional/narrower — rejected: unnecessary complexity for a flag that already does the right thing with one submodule left. |
