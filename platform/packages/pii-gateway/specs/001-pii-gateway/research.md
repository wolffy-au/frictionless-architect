# Research: PII Anonymization Gateway

Decision table for the implementation choices this plan needs that weren't already
settled by ADR-0014/ADR-0043/ADR-0044/ADR-0034. Each row is Decision / Rationale /
Alternatives considered (Principle XI).

| # | Decision | Rationale | Alternatives considered |
|---|----------|-----------|--------------------------|
| R1 | Presidio's default `en_core_web_lg` spaCy NER model, loaded once at module import and reused across calls (not per-call). | SC-005's 2-second ceiling is dominated by NER inference; spaCy model load is the expensive part (seconds) and must happen once, not per `scrub()` call. `en_core_web_lg` is Presidio's documented default and backs the `PERSON` and `LOCATION` recognizers FR-002 needs for name/physical-address coverage. `LOCATION` is broader than street addresses alone (cities, countries, landmarks also match) — accepted as a known false-positive source rather than a narrower custom recognizer, consistent with SC-002's tolerance for auto-redaction over missed PII. | `en_core_web_sm` (faster load, lower NER recall — rejected, risks false negatives on names) and per-call model instantiation (rejected — would blow the 2s budget on every call). |
| R2 | PHI categories covered via Presidio's built-in US-focused PHI-adjacent recognizers (`US_SSN`, `MEDICAL_LICENSE`) plus a small custom `PatternRecognizer` set for ADR-0014's named PHI language (medical record numbers, diagnosis codes) where no built-in recognizer exists. | Presidio ships general PII recognizers out of the box but not a complete PHI set; custom `PatternRecognizer`s are Presido's documented extension point and avoid a second detection library. | A dedicated PHI library (e.g. `scrubadub`'s HIPAA detectors) — rejected in ADR-0043 already (two detection engines is the complexity ADR-0043 explicitly avoided). |
| R3 | `Audit Entry` persisted as one JSON line per `scrub()` call to a local, git-ignored log file (`~/.local/state/frictionless-architect/pii-gateway-audit.jsonl`), not a database. | Matches ADR-0024's single-user local MVP scope and `llm-provider-config`'s precedent of git-ignored local files over a database; JSONL keeps each entry append-only and trivially greppable for maintainers. | SQLite (rejected — no query need justifies a schema/migration surface for a flat metadata-only record) and in-memory-only (rejected — FR-011 implies the log must survive process restarts for audit purposes). |
| R4 | Detector-category/failure-mode config stored the same way as `llm-provider-config`: a local TOML file (`~/.config/frictionless-architect/pii-gateway.toml`), read via `tomllib`/written via `tomli-w`, validated through a Pydantic v2 model. | Direct reuse of the established pattern (ADR-0034's Consequences/Implementation status) — no new format or validation approach to review. | A database-backed config store — rejected, same reasoning as R3; environment variables — rejected, too coarse for per-category/per-context settings. |
| R5 | Settings surface is a `create_settings_router(...)`-shaped FastAPI router (mirroring `llm_provider_config/router.py`), serving an HTML page plus a JSON API for category toggles and per-context failure-mode actions, mountable by the `portal` host or standalone (ADR-0020 update 2026-10-11). | ADR-0034 already established this exact mountable-router shape for a sibling shared package's settings UI; reusing it keeps the two packages' settings surfaces consistent for an operator switching between them. | A CLI-only config tool — rejected: FR-009/FR-003's "without a code change or redeploy" bar is already met by `llm-provider-config`'s web UI, and a second config UX pattern would be inconsistent. |
| R6 | A detector-engine exception inside `scrub()` is caught at the Presidio-call boundary and converted into a synthetic match (category `_ENGINE_ERROR`, zero-length span) which the normal failure-mode logic then processes alongside a real match — but because the span is zero-length, the redacted text for both `REDACTED_AND_PROCEEDED` and `FLAGGED_FOR_REVIEW`'s `REDACT` resolution replaces the **entire** input with `<_ENGINE_ERROR>` rather than running `anonymize()` over that span (ADR-0046). | Implements the spec's fail-closed Assumption with no separate match-dispatch code path — the existing failure-mode dispatch (auto-redact / flag-for-review) already branches on "was there a match," so an engine error reuses it instead of adding a third branch. Whole-text replacement is required because a span-based redaction over a zero-length span is a no-op: `anonymize()` has nothing to replace, so the real PII/PHI would survive untouched in the output (ADR-0046's bug fix). | A dedicated try/except that hard-blocks on engine error — rejected: ADR-0014's Alternatives considered already rejects hard-block as a global default, and a one-off exception to that for internal errors would be an undocumented inconsistency. Redacting only the zero-length span via the normal `anonymize()` path — rejected: this was the original implementation and the actual bug (ADR-0046) since it redacted nothing. |
| R7 | `PendingConfirmation.resolve(Resolution.ALLOW)` raises `EngineErrorAllowRejected` when the pending match is the synthetic `_ENGINE_ERROR` match, instead of returning `original_text` like it does for a real match (ADR-0046). `REDACT`/`EDIT` are unaffected. `modelling-specification`'s `resolve_pii` maps the exception to `409` and leaves the pending confirmation in place. | ALLOW on a real match is the architect's informed choice having seen what was flagged; the synthetic match carries no real detection to judge — the engine never ran — so allowing it through would hand back wholly uninspected text under the same "the architect decided this is fine" framing used for a real match, reopening the exact bypass R6's whole-text redaction closes for REDACT. | Treating ALLOW on an engine-error match identically to a real match (original behaviour) — rejected: silently permits the bypass fail-closed exists to prevent, just moved to the human resolution step. Escalating to a global hard-block on any engine error — rejected, same reasoning as R6's rejected alternative; out of scope, this only narrows the engine-error case's own three resolutions. |
