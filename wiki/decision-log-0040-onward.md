## Revisions and implementation notes

ADR-0040 (Accepted 2026-10-25, GH #129) fixes six whole-platform viewpoint
sweeps that had grown past readable (90–160 elements each) by giving the
model an explicit, first-class notion of bounded context. Every element
carries a `context:` tag (defaulting to the `platform` shared kernel when
absent; a vendored layer gets its own context named after its directory);
`check_context_coverage` warns on a first-party element that should carry
one but doesn't. One ArchiMate `Grouping` is generated per real context
(`generate_context_groupings`, `grp-ctx-<context>`) with a generated
`Aggregation` to each member — never hand-authored, so a context's
boundary can't drift out of sync with its membership. A view can declare
`split_by: context` to render one diagram per context instead of one
monolith. `include_neighbours: true` originally pulled in any element one
hop away too (but deliberately excluded from the view's own
viewpoint-conformance check) so a cross-context edge kept both endpoints
visible; applied to all six oversized views, including `view-product`,
which was briefly dropped entirely — the model has no
Product/Contract/Value/Material/`*Service` element to give that viewpoint
its own shape, so it rendered as a duplicate of content already on the
usage/service-realization views — before being kept after all: both it
and `view-application-usage` stay on the strength of being standard
ArchiMate 3.2 §14 viewpoints, the duplication accepted rather than
treated as grounds to drop the view. `include_neighbours: true` was
later removed from every split view (including these two), since it
inflated data-heavy contexts without a consistent size benefit on the
layer-spanning sweeps, and `view-information-structure` now uses
`derived: true` instead to recover cross-context edges without pulling
the inflating element set back in (see
[Architecture Model: Contexts](architecture-model-contexts.md) for the
full, current state). A generated context map
(`generate_context_map_relationships`, `view-context-map`) derives one
directed `Serving` edge per ordered context pair with at least one
crossing element-level relationship, becoming the new top-level overview
in place of the oversized full-platform views. Interfaces as the formal
boundary contract between contexts (Grouping → Interface → owning
Role/Component, Interface → consuming context) are deferred as a GH #129
follow-up rather than blocking this ADR, since the context map already
gives a coarse-grained version of the same dependency story. Left as an
open consequence: several per-context splits still exceed the ~60-element
target — the context owns a lot, or (`conformance-drift-assurance`) is by
design connected to almost every other context, being the compliance
cross-cutting concern
(`docs/adr/0040-bounded-contexts-as-generated-groupings.md` §Decision,
§Consequences). See [Architecture Model](architecture-model.md).

ADR-0041 (filed 2026-10-29, now Accepted, GH #68/#108/#142) records a deliberate
deviation from GH #68's filed plan rather than a retroactive rewrite of
it. GH #68's epic, as currently filed (#140-#151), re-platforms the
conversational agent onto a journey-API/Solution-Design architecture in
`reusable-architecture-library`; #142 frames adapting ADR-0037's agent for
that future shape as superseding its current form, not extending it in
place. No GH issue is filed for "give today's `delta.py` the ability to
return multiple structured, convention-grounded options" against the
architecture ADR-0037 actually shipped, and EPIC-003's own `spec.md`
(FR-001) only requires one clarifying question for a vague request, not
several ranked options. Given a demo-priority need now rather than waiting
on #142's unscheduled start, `delta.py`'s `propose_delta` was extended to
recognise a "way forward" request and return `{"options": [...]}` — 2-3
independently applicable candidate deltas, each with a `rationale` grounded
in existing element ids and/or Enterprise Convention Rule ids
(`architecture/model/conventions.yaml`). Each option is validated through the same
duplicate/pattern/metamodel pipeline the single-delta path already used
(`router.py`'s `Session.pending_options` and a new `POST
.../propose/select`) before the architect picks one. `spec.md`'s FR-001
text is deliberately left unrewritten, so a reader comparing spec to code
sees the gap and this ADR explaining it. Left open: whether the
options/`propose/select` shape migrates into #142's journey-API agent
as-is, gets redesigned, or is dropped as superseded, once that rework
starts; and that an option's `rationale` prose is never mechanically
checked against the ids it cites, only its `elements`/`relationships`
(`docs/adr/0041-structured-suggestion-options-in-delta-py.md` §Decision,
§Consequences). See [Conversational Model Authoring](modelling-specification.md).

ADR-0042 (Proposed 2026-10-29) records the maintenance tooling this wiki
itself depends on. Upkeep is delegated to single-purpose subagents under
`.claude/agents/`: read-only ones report, write-capable ones push a branch

Each platform package manifest pins explicit lower bounds for transitive

`pyproject.toml` independently of the shared `platform/poetry.lock` and kept

Consequences sections are still marked "DRAFT — confirm", and the
"Alternatives considered" section is empty pending a human

ADR-0043 (Accepted 2026-10-31, GH #136) picks Presidio for `pii-gateway`, which
ADR-0014 had left open. It wraps Presidio's regex and NER recognizers with this
platform's config surface and `ScrubResult` type, and adds first-party PHI
recognizers as Presidio custom recognizers. The cost is `spacy` plus a language
model, accepted because NER is what makes names and addresses detectable in free
text. `sether` was rejected as an unaudited, single-maintainer package in the PHI

being screened to another third party, and regex alone under-detects free text

§Alternatives considered).

ADR-0045 (Accepted 2026-11-04) makes the tool multi-tenant. Another
organisation's repo holds only its own model YAML and installs the package as a
dependency. `FRICTIONLESS_MODEL_DIR` sets the model root, and
`FRICTIONLESS_THIRD_PARTY_DIR`, `FRICTIONLESS_MODEL_NAME` and
`FRICTIONLESS_ADR_DIR` override the rest; their defaults follow the project root,
so another model cannot pick up this repo's vendored content. C4 diagrams are
skipped unless `FRICTIONLESS_C4_SYSTEM` names a system. `viewpoints.py` and the
puml and C4 projection move into the package, and the skill scripts become thin
wrappers. The `puml`/`c4` modules only print, and callers redirect. Consumers must
also list `llm-provider-config`, `digital-twin-knowledge-graph` and `pii-gateway`
as git dependencies, because they are not on PyPI. Splitting the model into its
own repo was rejected because model and tool change together; vendoring the
skill scripts was rejected because the copies would drift. The ADR records no
model impact (`docs/adr/0045-tool-model-separation-for-multi-tenant-use.md`
§Decision, §Alternatives considered). See
[Conversational Model Authoring](modelling-specification.md).

ADR-0046 (Accepted 2026-11-05) fixes `pii-gateway`'s fail-closed path. A
detector-engine error produces a synthetic zero-length match, so redacting only
that span changed nothing and sent uninspected text to the provider while
reporting it redacted. Redaction now replaces the whole text with
`<_ENGINE_ERROR>`, and `Resolution.ALLOW` raises `EngineErrorAllowRejected` for
that case because the architect has no real match to judge. `modelling-specification`
maps that to a 409 and leaves the confirmation open for redact or edit. `ALLOW` on a
real match is unchanged
(`docs/adr/0046-pii-gateway-engine-error-fail-closed-semantics.md` §Context,
§Decision). See [PII Gateway](pii-gateway.md).

ADR-0047 (Proposed 2026-11-08, GH #185) is a still-draft record for a decision
already shipped in two steps the same change window. Before GH #185, a chat
reply's free text was HTML-escaped and shown `pre-wrap`, so Markdown syntax
rendered literally. The first fix was a hand-rolled, dependency-free
client-side `renderMarkdown()` with its own fixed allowlist; the same-day
follow-up replaced it with server-side rendering — `router.py` runs the raw
reply through `markdown.markdown()` (`fenced_code`, `sane_lists`, `nl2br`) and
sanitises the output with `nh3.clean()` against an explicit allowlist (`p, br,
strong, em, code, pre, ul, ol, li, h1, h2, h3, a`; only `href`/`title` on `a`;
only `http`/`https`/`mailto` schemes; links forced to `target="_blank"
rel="noopener noreferrer"`), sending the sanitised `message_html` for the
client to insert directly. Both `markdown` and `nh3` become
`modelling-specification` runtime dependencies; once this ADR is ratified,
ADR-0044's test obliges at least `nh3` — the security-relevant sanitiser — a
`SystemSoftware` element, not yet added
(`docs/adr/0047-sanitised-markdown-rendering-for-llm-chat-text.md` §Context,
§Decision, §Consequences). See
[Conversational Model Authoring](modelling-specification.md).

ADR-0048 (Proposed 2026-11-08) records, after the fact, a CI security-scan

ADR-0049 (Accepted 2026-11-09, GH #198) resolves one of ADR-0012's deferred
solution decisions: the concrete cryptographic scheme and identity/certificate
model behind an ADR's human-attested signature. Because the platform's target
is a hosted, multi-tenant bank-governance deployment where different
organisations already run different identity infrastructure (personal GPG
keys, an internal PKI, a keyless OIDC-based scheme), the decision is a
**pluggable Attestation Method registry** rather than one fixed scheme: the
enabled method set is an admin-configured deployment property, and each
method owns its own identity binding and produces a verifiable signature over
an ADR's canonical content (Title, Status, Date, Decision, Consequences),
resolved to a named, accountable person. GPG/OpenPGP detached signatures are
the first implemented method, with identity resolved via the signer's PGP key
fingerprint against an admin-configured keyring mapping; a transition to
`Approved`/`Superseded` (ADR-0012's FSM) requires a signature from one
enabled, configured method, or it is blocked. Sigstore/cosign keyless signing
and an internal-CA X.509 PKI were both considered as the sole/first method and
rejected for that role (external-service dependency; CA provisioning ahead of
the single-user MVP's actual need) but remain viable later registry entries
(`docs/adr/0049-pluggable-adr-attestation-gpg-first.md` §Decision,
§Consequences, §Alternatives considered). See
[Governance & Constitution](governance-and-constitution.md).

ADR-0050 (Accepted 2026-11-09, GH #199) answers when FR-014's ADR-conflict
detection runs, which the spec had left open. A single trigger does not cover
every case: submission-only misses a contradiction that surfaces only once a
*later* ADR is accepted against an already-`Accepted` one, and on-demand-only
gives no guarantee that every ADR is ever checked at all. The decision runs
conflict detection on **three triggers**: automatic on submission (the
blocking gate FR-014 literally requires, before an ADR can leave `Draft`),
on demand (an architect re-checking a draft while iterating), and a weekly
scheduled audit sweep over the full accepted log that surfaces
post-acceptance contradictions to a human reviewer without ever auto-reverting
an already-`Accepted` ADR. The submission check is the only one that blocks a
transition; the sweep is advisory/reporting only, with its scheduling
mechanism and report format left to the eventual package's `plan.md`
(`docs/adr/0050-adr-conflict-detection-triple-trigger.md` §Decision,
§Consequences, §Alternatives considered). See
[Governance & Constitution](governance-and-constitution.md).

ADR-0051 (Accepted 2026-11-13) gives a view a way to *show* a derived
relationship — the ArchiMate 3.2 §3.5 case where a two-hop chain (`A
--r1--> B --r2--> C`) implies a weaker direct relationship without it being
modelled — without adding that relationship to the model.
`check_derived.py`'s advisory check already flagged the opposite failure
(an explicit relationship merely duplicating what a chain already implies)
and had already sketched this complementary feature in its own design
notes. `views.yaml` gains a `derived: true` flag; at render time `puml.py`
walks `pyArchimate.derivation.find_chains()` for two-hop chains with both
endpoints on the view but the intermediate element off it, and draws each
as a dashed `<<derived>>`-stereotyped arrow, visually distinct from every
modelled-relationship notation. The overlay is one-way and
render-time-only by design, not an interim step toward auto-promoting
derived relationships into the model: it is never written back into
`relationships.yaml` or the generated `.archimate`/XML, so the YAML source
stays the only authoritative record, at the accepted cost that the overlay
can change silently as the underlying chain changes with no reviewable
diff. The ADR also corrects two wrong issue citations it found in
`check_derived.py`'s own docstring — GH #140 and GH #146 both point at
unrelated issues, not the derived-relationships work they claimed to cite
(`docs/adr/0051-derived-relationship-overlay-rendering.md` §Context,
§Decision, §Consequences). See
[Architecture Model](architecture-model.md).

ADR-0054 (Accepted 2026-11-14, GH #84, part of epic GH #83) decides the
authentication mechanism, authorization model and tenancy boundary that
epic #83's multi-user access work needs, so later sub-issues implement one
shared approach instead of each inventing its own. **Authentication** is
standard OIDC, provider-agnostic rather than a self-hosted credential store:
Authorization Code + PKCE for the UI, client-credentials for automated
agents, with a FastAPI dependency validating the bearer JWT against the
IdP's JWKS and attaching verified identity claims — no server-side session
state. **Authorization** is RBAC (viewer/editor/owner/admin, epic #83's
scoped deliverable), expressed as Rego rules evaluated by the OPA engine
ADR-0019 already commits to (Proposed), living in the dedicated policy
component ADR-0013 already requires to stay separate from authentication;
the policy input is `(user, workspace_id, model_id, action)`, so later
ABAC-style conditions are additive Rego rules, not an engine change. The
**tenancy boundary is Workspace**: every model belongs to exactly one
workspace, role assignments are `(user, workspace)` pairs (not per-model),
and every policy check and Neo4j query is scoped by `workspace_id`. Model
impact, done in the same PR: a new `fn-authn-oidc` ApplicationFunction
(owned by `sub-portal`, the shared mounting surface) and `fn-authz-policy`
(owned by `sub-assurance`, where ADR-0019 already places the OPA wrapper),
linked by a `Flow` carrying ADR-0013's "identity attributes supply
authorization" rule; `store-akg`'s description now records that access to
it is scoped by workspace. No new top-level Workspace element is modelled —
at this model's own-platform granularity, tenancy is a data-shape fact
about `store-akg`, not a separate ArchiMate concept. A self-hosted
credential store, server-side sessions, pure ABAC with no role concept, and
per-model-only tenancy with no Workspace concept were all considered and
rejected. The ADR was originally filed as ADR-0053 but renumbered to 0054
after rebasing onto `develop`, which had independently filed its own
unrelated ADR-0053 (the browser-UI-tests decision above) in the meantime
(`docs/adr/0054-authn-authz-and-tenancy-approach.md` §Context, §Decision,
§Consequences, §Alternatives considered). See
[Architecture Model: Ecosystem](architecture-model-ecosystem.md) and
[Architecture Model: Artefact Flow](architecture-model-artefact-flow.md).
