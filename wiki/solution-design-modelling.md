## How it differs from Conversational Model Authoring

- **Different target artefact and function.** `fn-solution-modelling` reads
  and writes `do-solution-design`/`art-solution-design` in `store-patterns`
  — one Solution Design per session — never `do-candidate-arch`/`store-akg`
  or `architecture/model/`. `fn-conversational-authoring` keeps sole
  ownership of the enterprise knowledge graph; the spec's FR-001–FR-003 make
  the boundary a hard requirement, not just a naming convention
  (`specs/EPIC-003-conversational-model-authoring/002-solution-design-modelling/spec.md` §Requirements, §Clarifications).
- **Different home.** `fn-solution-modelling` is Assigned to `sub-library`
  (subsystem 2, `reusable-architecture-library`), not the
  `modelling-specification` package; its journey API, UI and agent are
  planned under `platform/packages/reusable-architecture-library/{ui,api}`.
  `reusable-architecture-library` itself does not exist yet as an extracted
  package, unlike `modelling-specification` (GH #108) — the spec is explicit
  that GH #68's "blocked on the monorepo pattern being proven" framing is
  now stale, since the pattern is already proven by four other extracted
  packages: `modelling-specification`, `controls-compliance-catalog`,
  `digital-twin-knowledge-graph`, and `schema-visualizer-api`; the spec
  itself does not depend on the extraction having happened, only its
  eventual implementation does (`specs/EPIC-003-conversational-model-authoring/002-solution-design-modelling/spec.md` §Assumptions). It shares the
  render path only: it Serves `fn-notation-engine` — implemented in
  `modelling-specification` — for live view rendering, mirroring that
  feature's own propose/validate/render loop rather than reusing its code.
- **MVP is free-form, not pattern composition.** Per GH #68's resolved open
  question, the architect describes changes directly; composing a Solution
  Design from a pattern/blueprint library and emitting an OSCAL System
  Security Plan (`fn-solution-compose`) are deferred to a later milestone
  and explicitly out of scope here (FR-011, `specs/EPIC-003-conversational-model-authoring/002-solution-design-modelling/spec.md` §Edge Cases).

## Scope and user stories

Three prioritised user stories (`specs/EPIC-003-conversational-model-authoring/002-solution-design-modelling/spec.md` §"User Scenarios & Testing"):

- **P1 — Describe a change, see it validated and rendered.** The architect
  describes a change in plain language; the agent proposes a candidate
  delta scoped to the open Solution Design, validates it against the
  ArchiMate metamodel, and renders the affected part live once accepted —
  the feature's core loop, with no other Solution Design or the enterprise
  knowledge graph touched (FR-001–FR-003, FR-010).
- **P1 — Role-scoped journey API with a policy stub.** One journey per
  role — Solution Architect (propose/accept/apply/render/query) and a
  read-only Compliance Officer/Auditor (render/query only) — with a stubbed
  policy check on every call (FR-004–FR-007); the real policy engine
  (ADR-0019/OPA) lands later, in milestone D (GH #148). A policy-check
  failure always surfaces as a refusal with an explanation, never an
  internal error, whether the underlying cause is a genuinely disallowed
  operation or just a stub returning a negative decision. The agent always
  acts under the calling architect's own identity, never with elevated
  permissions (FR-012).
- **P2 — Streams from day one.** The journey API responds as a sequence of
  incremental events (SSE or websocket) rather than one blocking reply,
  with a stub simulating realistic LLM latency visible as a delay before
  the first event rather than before the whole response (FR-008–FR-009),
  per GH #68 decision 6 (Principle IV: operations over 200ms must be
  asynchronous or justified).

**Edge cases** (`specs/EPIC-003-conversational-model-authoring/002-solution-design-modelling/spec.md` §"Edge Cases"): a request that would promote a
Solution Design change into the enterprise or domain model is refused
outright — that is milestone D's job (GH #149), not this feature's
(SC-002); a request to compose from a pattern/blueprint is explained as
out of scope rather than silently attempted or auto-converted; an empty
Solution Design is a valid thing for a Compliance Officer/Auditor to query,
not an error; a request from neither recognised role is refused outright
with no partial read or write; and an LLM call failing or timing out
mid-stream must show a clear failure, never a silently truncated response
or a partial, unvalidated delta applied.

## Open questions and deferred scope

- **Open question carried forward, not resolved here.** Whether
  `fn-solution-modelling` validates against `do-convention-rules` — the
  same enterprise/domain convention rules `modelling-specification`'s
  `validation/conventions.py` already applies to
  `fn-conversational-authoring` — is left for `/speckit-plan` under GH
  #140/#142, since a bounded Solution Design may not need the same rules
  unmodified (`specs/EPIC-003-conversational-model-authoring/002-solution-design-modelling/spec.md` §Assumptions).
- **Behave scenarios deferred to implementation, not written at specify
  time.** Following GH #108/ADR-0037's own precedent — that package's
  behave scenarios were written during implementation against the real
  running app, not during `/speckit-specify` — this spec's Acceptance
  Scenarios are the basis for behave scenarios to be written later,
  package-scoped under
  `platform/packages/reusable-architecture-library/tests/features/` once
  that package exists (`specs/EPIC-003-conversational-model-authoring/002-solution-design-modelling/spec.md` §Assumptions; `specs/EPIC-003-conversational-model-authoring/tasks.md`).
- **Not decided here either:** duplicate-detection, pattern-suggestion, and
  override-decision mechanics analogous to `fn-conversational-authoring`'s
  are not assumed to carry over by default — a decision for `/speckit-plan`
  if the Solution Design authoring loop needs equivalent safeguards
  (`specs/EPIC-003-conversational-model-authoring/002-solution-design-modelling/spec.md` §Assumptions). Multi-architect concurrent editing of the same
  Solution Design, and locking/merging semantics, are out of scope (GH
  #151, milestone D).
