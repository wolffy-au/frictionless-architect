## What this is

`architecture/model/` holds the **canonical** architecture model for the
platform, stored as graph-loadable YAML. Every other form — the ArchiMate XML,
the C4 / PlantUML diagrams, and (later) the Neo4j seed — is a generated
projection of these files (`architecture/model/README.md` §"Architecture
model"). The decision and its rationale are recorded in
[ADR-0007](decision-log.md) (graph-loadable YAML is canonical; the `.xml`
exchange format is chosen over Archi-native `.archimate` for diff legibility)
and [ADR-0008](decision-log.md) (`type` is a bare ArchiMate 3.2 concept name).

```text
elements.yaml + relationships.yaml + views.yaml   (canonical, hand-edited)
   └─▶ build.py ─▶ frictionless-architect.xml ─▶ validate.py
                        ├─▶ diagram-c4        ─▶ diagrams/c4/*.puml / .svg
                        └─▶ diagram-archimate ─▶ diagrams/<layer>/<view>.puml / .svg
```

(`architecture/model/README.md` §"Architecture model"). The root
`build.py`, `render_diagrams.py` and the validator are thin entry points into
the `modelling-specification` package's CLI; model loading, merging,
validation and rendering live there
(`architecture/model/README.md` §"Architecture model";
`architecture/model/build.py:1-56`;
`platform/packages/modelling-specification/src/modelling_specification/cli.py:89-113`).
The build checks the ArchiMate 3.2 relationship matrix and project-specific
motivation conventions
(`platform/packages/modelling-specification/src/modelling_specification/model_io.py:346-379`; see
[Skeleton § Goal and outcomes](architecture-model-skeleton.md#goal-and-outcomes-the-motivation-spine)). The
current merged model is 515 elements, 1029 relationships and 66 views
(re-counted 2026-10-24 against a clean `build.py` run; the model validates
with no metamodel or referential-integrity violations). Of those, 280
elements and 658 relationships are hand-authored in this repo's own
`elements.yaml`/`relationships.yaml` plus `views.yaml`/`views-viewpoints.yaml`
(sections A–C, E and F, plus the IT4IT touchpoint bridge, plus one generic
view per standard viewpoint — see [Architecture Model: Context-Level Viewpoints & Bounded Contexts](architecture-model-contexts.md)); 93
elements and 136 relationships are generated into
`architecture/model/gh-roadmap/` by `import_gh_roadmap.py` (see "GitHub
roadmap layer" below); and 142 elements and 235 relationships are the
vendored IT4IT reference model, merged in at build time
([ADR-0029](decision-log.md) — see [Architecture Model: Build Pipeline & IT4IT Merge](architecture-model-build-it4it.md)). The generated
`frictionless-architect.xml` is committed but never hand-edited — same status
as the `.puml` / `.svg` diagrams.

Schema rules (`architecture/model/README.md` §"Schema";
`architecture/model/elements.yaml:7-10`):

- **`type`** — a bare ArchiMate 3.2 concept name (`Driver`, `Goal`, `Outcome`,
  `Principle`, `Constraint`, `Requirement`, `Capability`, `ValueStream`,
  `BusinessProcess`, `ApplicationComponent`, `ApplicationFunction`,
  `DataObject`, `Grouping`, …). Case-insensitive; the model loader
  canonicalises against the supported ArchiMate types
  (`platform/packages/modelling-specification/src/modelling_specification/model_io.py:81-92`).
- **`id`** — a stable kebab id, hashed to a deterministic UUID so regeneration
  never churns identifiers or diagrams. *Never renumber a live id.*
- **`name` / `desc`** — top-level keys, not inside `props`. Double-quote any
  value containing a `#` that follows a space (for example
  `desc: "… (GH #45)."`): in an unquoted YAML scalar that `#` starts a
  comment, so the text is silently cut off and the truncation shows up in
  every generated diagram (`architecture/model/README.md` §"Schema").
- **`context`** — optional top-level key on an element: its bounded context.
  Defaults to `platform` for first-party files and to the layer directory's
  name for `third_party/<name>` and `gh-roadmap/`; written to the XML as a
  `context` property. First-party contexts are `platform` (the shared
  kernel — motivation, strategy, business layer, infrastructure, migration,
  external systems, shared stores) plus the eight platform packages
  (`controls-compliance-catalog`, `reusable-architecture-library`,
  `digital-twin-knowledge-graph`, `architecture-governance`,
  `conformance-drift-assurance`, `modelling-specification`,
  `schema-visualizer-api`, `llm-provider-config`), each owning its subsystem,
  its functions, interface and the artefacts it writes. A view's `context:`
  (default `[platform]`) limits which contexts its `include_types` sweep
  draws from; `members` are always honoured, and `platform` in a view's
  `context:` covers the whole first-party family
  (`architecture/model/README.md` §"Schema"). `check_context_coverage`
  (GH #129) warns at build time on a first-party Application/Technology/
  BusinessObject element with no explicit `context:` and no recorded
  exemption, so a package can't silently fall back to the shared `platform`
  context by omission. Section C–F elements now carry that tag explicitly —
  for example the capabilities, business processes, business functions and
  business objects of the policy/OSCAL pipeline are tagged
  `controls-compliance-catalog`, the drift, release-gate and assessment
  elements `conformance-drift-assurance`, the pattern/blueprint/solution
  elements `reusable-architecture-library`, and the graph/ledger/Neo4j
  elements `digital-twin-knowledge-graph`
  (`architecture/model/elements.yaml`, e.g. `cap-control-catalog`,
  `bfn-release-enforcement`, `bo-architecture-pattern`, `sw-neo4j`).
- **`exclude_elements`** on a view (optional) — a list of patterns that drop
  otherwise-selected elements (via `members` or `include_types`) before nodes
  and connections are built. Each entry may give `type` (ArchiMate concept
  name), `id` or `id_prefix`; an element is excluded when every key given in
  an entry matches (omitted keys are wildcards). This is the fix for
  `include_types` picking up a vendored layer sharing the same ArchiMate
  type as a first-party one — e.g. `third_party/it4it` contributes 42
  Capability / 35 Outcome / 28 ValueStream elements, all `it4it-`-prefixed,
  so `{id_prefix: "it4it-"}` keeps those off a first-party view without
  reverting to an explicit `members` allow-list that silently drops any new
  first-party element of that type until someone remembers to add it (GH
  #117). Views that sweep by `include_types` under the default
  `context: [platform]` no longer need that entry — the default scope already
  excludes vendored layers — so `views.yaml` dropped the redundant
  `{id_prefix: "it4it-"}` excludes (GH #129 step 7;
  `architecture/model/views.yaml`). This is distinct from the
  relationship-level `exclude` key below.
- **`props`** — string→string. `c4` / `c4-label` for the C4 projection,
  `access_type` (`Read` | `Write` | `ReadWrite`) on `Access` relationships,
  `requirement-type`, and `archimate-analogue` on a BusinessObject whose
  *content* in the managed estate's model is an Implementation & Migration
  concept (Plateau, Gap, …). It is kept as a tag so this model's own
  Plateaus stay free to mean states of the platform itself
  (`architecture/model/README.md` §"Schema"). The strategy/drift business
  objects use it; see [Skeleton](architecture-model-skeleton.md).
- **`label`** on a relationship shows on ArchiMate diagrams and is the default
  C4 edge label; `props.c4-label` overrides it in the C4 projection only.
- **`exclude`** on a view (optional) — a list of type+pair patterns
  (`type` / `source_type` / `target_type` / `source` / `target`, all optional
  and AND-combined per entry) matched against each in-scope relationship
  before it's drawn as a view connection; a relationship is suppressed when
  every key given in an entry matches, and omitted keys are wildcards
  (`platform/packages/modelling-specification/src/modelling_specification/model_io.py:380-420,466-610`, GH #20). Added
  because the renderer draws any relationship whose both
  endpoints are in scope, so a mesh that is core to one view's story (e.g.
  the 8-edge capability-to-capability `Serving` mesh on `view-capability`)
  leaks identically into every other view that happens to share ≥2 of those
  capabilities as members. Ten views each declare
  `exclude: [{type: Serving, source_type: Capability, target_type:
  Capability}]` to drop that incidental mesh:

  - Strategy
  - the four per-stream Value Stream views (`6a`–`6d`)
  - Outcome Realization
  - Requirements Realization
  - Subsystems & Capabilities
  - IT4IT: Capability Bridges

  (`architecture/model/views.yaml`.)
- **`viewpoint`** on a view (optional) — a standard ArchiMate viewpoint slug
  from `.claude/skills/model-archimate/reference/archi-viewpoints.xml`
  (`poetry run python .claude/skills/model-archimate/scripts/viewpoints.py
  list`). `build.py` holds that view to the viewpoint's allowed concepts and
  fails on a stray one. `viewpoint: custom` marks a deliberate cross-layer view
  (not checked), and omitting the key also skips the check
  (`architecture/model/README.md` §"Schema"). The tag lives only in
  `views.yaml`, because the exchange format does not preserve it in the
  generated XML. Since PR #62, **no view uses `custom`**: every platform view is
  held to a standard viewpoint. The schema still documents the option.
- **`no_direction`** on a view (optional) — relationship types to draw
  undirected on that view only, instead of `diagram-archimate`'s default
  `Up`/`Right` layout hint. It is for graphs that aren't a one-way sequence,
  where the rank hint would fight itself (`architecture/model/README.md`
  §"Schema").
- **`max_width`** on a view (optional) — an integer pixel width, rendered as
  PlantUML's `scale max <px> width`. It is for long chains that would
  otherwise scroll horizontally, and is used by Delivery Choreography
  (`architecture/model/README.md` §"Schema").

The model loader accumulates invalid model entries and reports collected
build errors before writing or validating the exchange-format model
(`platform/packages/modelling-specification/src/modelling_specification/model_io.py:106-126,633-670,854-872`).

## GitHub roadmap layer

`import_gh_roadmap.py` reads GitHub milestones, issues and releases through an
authenticated `gh` and writes `gh-roadmap/{elements,relationships,views}.yaml`:
**generated**, committed, deterministic and never hand-edited. Milestones become
Plateaus (`plat-<slug>-<n>`), issues with their own milestone become Work
Packages (`wp-<slug>-gh-<n>`), published releases become Deliverables
(`del-release-<tag-slug>`), and per-milestone views are emitted alongside.
A failed or incomplete read writes nothing; `--check` exits 1 if the files
would change; run `build.py` and `render_diagrams.py` afterwards. Gaps, the
**Current State** Plateau (renamed from "Baseline") and Strategy elements
stay hand-authored. The mapping and
ownership rules are ADR-0035 (`architecture/model/README.md` §"GitHub roadmap
layer"; `docs/adr/0035-github-roadmap-as-implementation-migration-layer.md`).
See [Architecture Overview](architecture.md).
