## Revisions and implementation notes

ADR-0031 carves a **scoped exception** out of ADR-0014. The OSCAL
conversion pipeline (`controls-compliance-catalog` spec 001, FR-016) sends
verbatim policy and regulatory-standard text to an LLM without redaction. The
reasoning is that authored, organisation-owned governance text is a
different category from personal data swept up by collaboration-tool
capture. ADR-0014's text is unchanged, and its gateway stays mandatory on
every other LLM path. The ADR says to revisit if such documents turn out to
routinely carry PII/PHI
(`docs/adr/0031-fr016-no-redaction-for-policy-documents.md`).

ADR-0032 settles the ArchiMate namespace (GitHub issue #51). The Open Group's
3.1 exchange-format XSDs keep the `http://www.opengroup.org/xsd/archimate/3.0/`
namespace, but the bundled copies had been hand-edited to a 3.1 namespace.
The fix restores the XSDs to the official files and accepts only the 3.0
namespace, defined once as `ARCHIMATE_NS`. Any other namespace is rejected
loudly rather than parsing to an empty model, which had violated
constitution Principle VII. Both alternatives were rejected: moving to 3.1,
because no conforming tool emits it, and accepting both, because that would
hide schema drift (`docs/adr/0032-archimate-exchange-namespace-3-0.md`).
ADR-0032 now describes itself as complementing ADR-0022 rather than being
independent of it. The XSD validation would also reject a foreign namespace.
The namespace check runs first and short-circuits, though, so the user gets
one clear error instead of a cascade of XSD failures
(`docs/adr/0032-archimate-exchange-namespace-3-0.md` §Consequences). See
[Data Model](data-model.md) and [Visualizer Service](visualizer-service.md).

ADR-0033 (Accepted 2026-09-26) established value-recipient-oriented streams,
moving stages between streams rather than duplicating them. The 2026-10-17
Goal/Sub-Goal/Outcome split kept five streams and 11 stages; streams now
realize one or more outcomes under their sub-goal, rather than maintaining a
strict one-stream-per-outcome count. Per-role streams, a single stream and
duplicated stages were all considered and rejected
(`docs/adr/0033-value-streams-per-outcome.md`). See
[Architecture Model: Skeleton](architecture-model-skeleton.md).

ADR-0034 (Accepted 2026-10-03) answers where functionality shared by several
subsystem packages lives, and how LLM provider keys are stored. Each shared
concern gets its own sibling package. Keys live in the OS keychain through `keyring`,
and the settings file holds only a keyring entry reference. An implementation
note amends the keychain-only rule with a labelled, logged environment-variable
fallback for headless environments. `.env` is still not read
(`docs/adr/0034-shared-packages-and-llm-provider-config.md` §Decision,
§Implementation status). The ADR's own text and `ARCHITECTURE.md` §4 now list
GitHub Copilot among the day-one providers; the model's
`sub-llm-provider-config` element description still names only four
(`architecture/model/elements.yaml`, not a source of this page). Its UI
bullet was reworded on 2026-10-11 alongside the ADR-0020 update (GH #120):
rather than being embedded by each subsystem UI, the settings router is now
mounted once by the `portal` host with every package's components
registered, and a package may also mount it in its own standalone `app.py`
(`docs/adr/0034-shared-packages-and-llm-provider-config.md`). See
[LLM Provider Configuration](llm-provider-config.md) and
[Portal](portal.md).

ADR-0035 (Accepted 2026-10-05, GH #95) makes the GitHub roadmap the source of
truth for the Implementation & Migration layer, which had drifted when
hand-authored. `architecture/model/import_gh_roadmap.py` reads milestones,
milestone issues and published releases through `gh` and writes the committed,
deterministic `architecture/model/gh-roadmap/` layer: milestones become
Plateaus, issues with their own milestone become Work Packages, releases become
Deliverables. `build.py` merges the layer like the vendored models, and nothing
in it is hand-edited. Gaps, the baseline Plateau, Strategy elements and the
Triggering between Plateaus stay hand-authored; Course of Action does too,
because GitHub cannot tell an epic from a task. A failed or incomplete read
writes nothing, and `--check` reports drift. The same cut-over retired
`plat-runtime-mvp` and `plat-runtime-target` in favour of the generated
Plateaus (`docs/adr/0035-github-roadmap-as-implementation-migration-layer.md`
§Decision; `ARCHITECTURE.md` §8.3). The Realization rule was extended
(spec 003 clarification, 2026-10-12): an issue closed as not-planned or a
duplicate stays on the unreleased Deliverable rather than being realized, and
a release realizes every Plateau it delivered a Work Package for. A second
clarification (2026-10-17) stops an epic's children from each redrawing the
epic's edge: a Work Package whose Aggregation root resolves to the same
Deliverable emits no Realization edge of its own, and realizes it structurally
through the Aggregation chain instead
(`docs/adr/0035-github-roadmap-as-implementation-migration-layer.md` §Decision). See
[Architecture Model](architecture-model.md).

ADR-0036 (Accepted 2026-10-08, GH #109) names the convention that was
missing when `art-` drifted into meaning two different things: the genuine
ArchiMate `Artifact` type (code packages, deployment artefacts) and,
separately, 35 `DataObject` elements prefixed `art-` for the business term
"artefact". The collision caused a real mistyping in GH #108's planning work,
caught only by manual review. The decision: a prefix always names the
element's own ArchiMate type, never a business synonym or role name that
could be mistaken for a different type. The 35 colliding `DataObject`
elements — the artefact input/output pipeline: policy documents, OSCAL
catalogs/profiles, baselines, blueprints, the ADR/roadmap/gate-decision
chain — are renamed `do-*`; `art-*` now exclusively denotes `Artifact`-typed
elements (`art-flat-src`, `art-pkg-*`, `art-tech-oscal-workspace`,
`art-tech-ledger-file`). Redefining `art-` to mean "artefact" instead was
rejected: `Artifact` is the rarer group and the name an ArchiMate-literate
reader expects it to mean
(`docs/adr/0036-element-id-prefix-scheme.md` §Decision, §Alternatives
considered). See [Architecture Model: Artefact Flow](architecture-model-artefact-flow.md).

ADR-0037 (Proposed 2026-10-10, GH #108) is the Constitution-Check-mandated
record for the conversational model-authoring agent's five load-bearing
decisions: it lives in a new `platform/packages/modelling-specification`
sibling package (the same shape as `controls-compliance-catalog`); root's
`build.py`/`render_diagrams.py` and the `model-archimate` skill's
`validate.py` all become thin wrappers shelling into that package's CLI
(`poetry run --directory platform python -m modelling_specification.cli
build|render|validate`), giving the YAML load/merge/validate and view-render
logic one implementation instead of three while keeping ADR-0001's
root-never-imports-a-platform-package boundary; Enterprise Convention Rules
(interposed-element shapes, naming/altitude conventions) move to a new,
inspectable `architecture/model/conventions.yaml`, aggregated under
`store-frameworks` alongside `do-metamodel`, while the fixed ArchiMate 3.2
metamodel rules stay sourced from pyArchimate; an architect overriding a
flagged objection (convention-fail or confirmed non-duplicate) auto-drafts a
`Status: Proposed` ADR stub rather than appending to `store-ledger`, because
an override is an architecture-governance decision, not controls/compliance
evidence, and `adr-auditor` already sweeps for exactly this; and the feature
gets its own business-layer wiring — `vs-intent-to-model` ValueStream and
`process-conversational-authoring` BusinessProcess, served by the existing
`coa-executable-governance` course of action, realized by the already-built
`fn-conversational-authoring` ApplicationFunction
(`docs/adr/0037-conversational-model-authoring-architecture.md` §Decision).
The ADR notes `plan.md` provisionally cited this decision as "ADR-0036"
before that number was taken by the unrelated element-id-prefix-scheme ADR
during a rebase; both `plan.md` references were corrected to ADR-0037
alongside filing this record. See
[Conversational Model Authoring](modelling-specification.md).

ADR-0038 (Accepted 2026-10-18, GH #69/#45) resolves a three-way disagreement
about roles: spec 001 named a single undifferentiated "Architect" persona;
`architecture/model/` section B already modelled six `BusinessRole`s
(Enterprise Architect, Solution Architect, Security Architect/Threat
Modeller, Developer, Compliance Officer/Auditor, Platform Operations); and
GH #45's role-journey list shared only "Solution architect" with the model.
Because journey APIs are designed one per role and access control derives
from them (FR-016), the maintainer decided the section-B six are canonical:
GH #45's entries (policy conversion admin, policy author, patterns admin,
security assessor, pattern contributor, implementation contributor, solution
architect) are modelled as `Specialization`s of a section-B role, not a
parallel role set, adding six new `BusinessRole` elements with one
`Specialization` edge each. Spec 001's single "Architect" persona is split
across all three architect roles, with the ADR-review/attestation/drift
journeys narrowed to Enterprise Architect specifically, the only one whose
function matches those journeys
(`docs/adr/0038-section-b-roles-canonical.md` §Decision). Re-cutting the
`bfn-*` functions the new roles touch is out of scope here, tracked as epic
item 0 of GH #68.

ADR-0039 (Proposed 2026-10-24, GH #68/#138) distinguishes the new
conversational *solution* modelling feature from ADR-0037's conversational
*candidate-architecture* authoring, which a naive reading could conflate —
both are natural-language, metamodel-validated and live-rendered. The new
`fn-solution-modelling` edits a `do-solution-design` in `store-patterns` for
the Solution Architect; ADR-0037's `fn-conversational-authoring` edits a
`do-candidate-arch` in `store-akg` for the Enterprise Architect. Giving
`role-sa` its own correctly-scoped function also corrected ADR-0037/spec
004's framing: the three elements it described as a "shared standing
process" jointly assigned from `role-ea` and `role-sa` are renamed
"Conversational Candidate Architecture Authoring" (ids unchanged), and the
unused `role-sa` Assignment to them is dropped in favour of a new `Serving
fn-solution-modelling -> if-modelling-authoring-ui` edge. `fn-solution-modelling`
is Assigned to `sub-library` (subsystem 2), alongside the structured
`fn-solution-compose` it sits next to, and Serves `fn-notation-engine` in
`sub-modelling` for rendering. A new `process-conversational-solution-modelling`
composes into the existing `bfn-solution-design`, alongside
`process-solution-design`, rather than adding a new `BusinessFunction` — same
business capability, two authoring modes. The agent edits one
`do-solution-design` at a time; it never writes `architecture/model/` itself
(`docs/adr/0039-conversational-solution-modelling-scope.md` §Decision). Left
open: the chat/live-view UI shell (GH #140) and whether the agent reads
`do-convention-rules` the way ADR-0037's does — revisit once #140 or #142
needs an answer. See [Conversational Model Authoring](modelling-specification.md).

ADR-0040 (Accepted 2026-10-25, GH #129) fixes six whole-platform viewpoint
sweeps that had grown past readable (90–160 elements each) by giving the
model an explicit, first-class notion of bounded context. Every element
carries a `context:` tag (defaulting to the `platform` shared kernel when
absent; a vendored layer gets its own context named after its directory);
`check_context_coverage` warns on a first-party element that should carry
one but doesn't. One ArchiMate `Grouping` is generated per real context
(`generate_context_groupings`, `grp-ctx-<context>`) with a generated
`Aggregation` to each member — never hand-authored, so a context's
boundary can't drift out of sync with its membership. A view can declare
`split_by: context` + `include_neighbours: true` to render one diagram per
context instead of one monolith, with any element one hop away pulled in
(but deliberately excluded from the view's own viewpoint-conformance
check) so a cross-context edge keeps both endpoints visible. Applied to
five of the six oversized views; the sixth, `view-product`, is dropped —
the model has no Product/Contract/Value/Material/`*Service` element to
give that viewpoint its own shape. A generated context map
(`generate_context_map_relationships`, `view-context-map`) derives one
directed `Serving` edge per ordered context pair with at least one
crossing element-level relationship, becoming the new top-level overview
in place of the oversized full-platform views. Interfaces as the formal
boundary contract between contexts (Grouping → Interface → owning
Role/Component, Interface → consuming context) are deferred as a GH #129
follow-up rather than blocking this ADR, since the context map already
gives a coarse-grained version of the same dependency story. Left as an
open consequence: several per-context splits still exceed the ~60-element
target — the context owns a lot, or (`conformance-drift-assurance`) is by
design connected to almost every other context, being the compliance
cross-cutting concern
(`docs/adr/0040-bounded-contexts-as-generated-groupings.md` §Decision,
§Consequences). See [Architecture Model](architecture-model.md).

ADR-0041 (Proposed 2026-10-29, GH #68/#108/#142) records a deliberate
deviation from GH #68's filed plan rather than a retroactive rewrite of
it. GH #68's epic, as currently filed (#140-#151), re-platforms the
conversational agent onto a journey-API/Solution-Design architecture in
`reusable-architecture-library`; #142 frames adapting ADR-0037's agent for
that future shape as superseding its current form, not extending it in
place. No GH issue is filed for "give today's `delta.py` the ability to
return multiple structured, convention-grounded options" against the
architecture ADR-0037 actually shipped, and EPIC-003's own `spec.md`
(FR-001) only requires one clarifying question for a vague request, not
several ranked options. Given a demo-priority need now rather than waiting
on #142's unscheduled start, `delta.py`'s `propose_delta` was extended to
recognise a "way forward" request and return `{"options": [...]}` — 2-3
independently applicable candidate deltas, each with a `rationale` grounded
in existing element ids and/or Enterprise Convention Rule ids
(`architecture/model/conventions.yaml`). Each option is validated through the same
duplicate/pattern/metamodel pipeline the single-delta path already used
(`router.py`'s `Session.pending_options` and a new `POST
.../propose/select`) before the architect picks one. `spec.md`'s FR-001
text is deliberately left unrewritten, so a reader comparing spec to code
sees the gap and this ADR explaining it. Left open: whether the
options/`propose/select` shape migrates into #142's journey-API agent
as-is, gets redesigned, or is dropped as superseded, once that rework
starts; and that an option's `rationale` prose is never mechanically
checked against the ids it cites, only its `elements`/`relationships`
(`docs/adr/0041-structured-suggestion-options-in-delta-py.md` §Decision,
§Consequences). See [Conversational Model Authoring](modelling-specification.md).

ADR-0042 (Proposed 2026-10-29) records the maintenance tooling this wiki
