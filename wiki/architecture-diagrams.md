This topic covers how the canonical model's views map to ArchiMate viewpoints
and get rendered into `.puml`/`.svg` diagrams, and how to regenerate them. For
what the model itself *means* — elements, relationships, the four content
sections — see [Architecture Model](architecture-model.md).

## Views and diagrams

21 ArchiMate views cover the merged model — 17 declared in this repo's own
`views.yaml` (sections A–C plus the IT4IT touchpoint bridge, see
[Architecture Model](architecture-model.md)) plus 4 declared in
`third_party/it4it/views.yaml` for the vendored IT4IT reference (section D),
loaded the same way its elements/relationships are ([ADR-0029](architecture.md)).
The C4 context and container diagrams are **not** views — `render_diagrams.py`
projects them via `diagram-c4` with `--system "Frictionless Architecture
Platform"` (`architecture/model/README.md` §"Regenerate").

### The TOGAF Phase A vision set

Seven of the platform's own 17 views are a TOGAF ADM Phase A "Architecture
Vision" set, each held to its matching standard ArchiMate viewpoint and
rendered under `diagrams/vision/`. Their diagram files carry a `1-`…`7-`
prefix so a directory listing sorts in Phase A reading order
(`architecture/model/views.yaml` — each view's `diagram:` key):

| # | View | Viewpoint | Diagram | Covers |
|---|---|---|---|---|
| 1 | Stakeholder | `stakeholder` | `vision/1-stakeholder` | Who holds which driver, the assessments that make each urgent, and the goal + outcome they drive toward |
| 2 | Motivation | `motivation` | `vision/2-motivation` | The whole motivation model: stakeholders, assessments, drivers, goal, outcome, principles, requirements, constraints |
| 3 | Goal Realization | `goal_realization` | `vision/3-goal-realization` | Goal → outcome, and how principles/requirements/constraints realize it |
| 4 | Strategy | `strategy` | `vision/4-strategy` | Resources → capabilities → courses of action, the value stream as a single element, and the outcome |
| 5 | Capability Map | `capability` | `vision/5-capability-map` | The eight capabilities and their `Serving` dependency order |
| 6 | Value Stream — Governed Architecture Delivery | `value_stream` | `vision/6-value-stream` | The stream's six stages (`Composition` + `Triggering` sequence, with a `Reconcile → Specify` feedback `Flow`), the capabilities that `Serve` each stage, the recipient stakeholders, and the outcome it `Realizes` |
| 7 | Outcome Realization | `outcome_realization` | `vision/7-outcome-realization` | Business processes → capabilities → value stream → outcome, the end-to-end realization chain |

The vendored IT4IT views follow the same convention in their own repo
(`1-stakeholder` … `4-outcome-realization`) — see
[IT4IT Reference Model](it4it-model.md).

There used to be an eighth vision diagram, **Vision — Policy-to-Runtime
Controls Lifecycle** (`view-vision-controls-lifecycle`, GH #7). It is gone.
It carried the same objects and relationships as `Business — Controls &
Compliance Catalog`, grouped by BusinessFunction rather than by role. The
two were merged by assigning each role to the BusinessFunction it performs
instead of to individual processes. The single remaining view then nests
where the structure allows (`architecture/model/views.yaml` — the
`view-business-controls-catalog` note):

- **Function > Role > Process** where one role owns a function outright,
  e.g. Policy-to-OSCAL Conversion > Compliance Officer.
- **Flat Function > Process**, with an `Assignment` arrow to each role,
  where a function's steps are split across roles. Pattern & Blueprint
  Traceability is split between the Enterprise and Solution Architects.
- **Flat Function > Process** with no role where the function is automated:
  Release Controls Enforcement and Drift Management.

`Business — Controls & Compliance Catalog` is now the **single consolidated
picture** of a control's journey from authored policy through to operational
assurance.

### The remaining views

Of the other ten platform-model views:

- `Delivery Choreography` is the only one still marked `viewpoint: custom`.
  It is a deliberate cross-layer cut that isn't held to a standard
  allow-list.
- The five per-stage `Artefact Flow — …` views are
  `application_cooperation`.
- `Business — Controls & Compliance Catalog` is
  `business_process_cooperation`.
- `Architecture Skeleton` and `Subsystems & Capabilities` are
  `outcome_realization`. Each is a `BusinessProcess`/`ApplicationComponent`
  → `Capability` realization cut, which the standard Outcome Realization
  allow-list (`Capability` + business/application elements) matches even
  with no `Outcome` element on the view.
- `IT4IT: Capability Bridges` (see below) is `capability`, a pure
  `Capability`-to-`Capability` cut across first-party and IT4IT
  capabilities.

(`architecture/model/views.yaml`). Rendered `.puml` / `.svg` files land under
`architecture/model/diagrams/`, in per-ArchiMate-layer subfolders
(`application/`, `business/`, `c4/`, `cross-layer/`, `vision/`).

The Controls & OSCAL stage is now drawn as **two** application-layer views
rather than one, so that creating OSCAL and resolving it don't crowd a
single diagram (`architecture/model/views.yaml` — `view-artefact-oscal`,
`view-artefact-oscal-resolve`):

- `Artefact Flow — Controls & OSCAL` (`application/artefact-oscal`) shows
  the LLM Provider serving AI-assisted Markdown conversion. Trestle then
  serves the assemble round-trip into catalog and profile. The view also
  holds the golden-dataset baseline catalog and profiles.
- `Artefact Flow — OSCAL Profile Resolution`
  (`application/artefact-oscal-resolve`) shows Trestle's `profile-resolve`
  turning a profile and its catalog into a resolved catalog. It sits next to
  FedRAMP's pre-resolved baselines, which serve as validation data.

The C4 context and container diagrams follow the same remodel. The
`Regulatory Content Sources` external system is gone. On the context
diagram, upstream text now appears as an external **data store**,
"Regulatory Standard" (`SystemDb_Ext`), rather than as a system. Both
diagrams show `compliance-trestle` and the LLM Provider as the external
systems serving OSCAL conversion, per [ADR-0030](architecture.md)
(`architecture/model/diagrams/c4/context.puml`,
`architecture/model/diagrams/c4/container.puml`). See [Architecture Model](architecture-model.md)
§"Controls & OSCAL" for the underlying elements.

Seven views — `Strategy`, `Value Stream — Governed Architecture Delivery`,
`Outcome Realization`, `Architecture Skeleton`, `Delivery Choreography`,
`Subsystems & Capabilities`, `IT4IT: Capability Bridges` — also declare an
`exclude:` pattern (`{type: Serving, source_type: Capability, target_type:
Capability}`). The pattern suppresses the 7-edge capability-to-capability
`Serving` mesh. That mesh is `Capability Map`'s own story, but it would
otherwise appear on every other view that shares ≥2 capabilities as members,
because `build.py`'s default rule draws any relationship whose endpoints are
both in scope (GH #20; see [Architecture Model](architecture-model.md) for the
`exclude:` schema).

Several of the platform-model views deliberately scope a type by explicit
`members` rather than `include_types`, because the vendored IT4IT model adds
many more elements of that same ArchiMate type — an `include_types` scoping
would silently pull IT4IT elements into a platform-only view. This affects
every view that includes `Outcome` (IT4IT adds a second one,
`it4it-outcome-digital-product`), `Capability` (42 more), or `ValueStream`
(36 more: 7 streams + 29 stages) — e.g. `Stakeholder`, `Strategy`,
`Capability Map`, `Value Stream — Governed Architecture Delivery`,
`Outcome Realization` and `Architecture Skeleton` all switched their
Outcome/Capability/ValueStream scoping to `members` for this reason
(`architecture/model/views.yaml` — see the inline notes on `view-stakeholder`,
`view-strategy`, `view-capability`, `view-value-stream`, `view-outcome-realization`,
`view-skeleton`).

An earlier "IT4IT Alignment" monolith view (79 elements, everything at once)

## Regenerating

```bash
poetry run python architecture/model/build.py           # YAML -> XML (+ validate)
poetry run python architecture/model/render_diagrams.py # XML -> every .puml / .svg
```

`render_diagrams.py` reads each view's `diagram:` key (one `.puml`/`.svg` pair
per view) plus the two C4 diagrams. It replaces the earlier manual per-view
`plantuml` loop.

The script is **incremental**. It generates each view's `.puml` in memory and
compares it with the committed file. Only a view whose `.puml` actually
changed is rewritten and has its `.svg` re-rendered, since the
PlantUML/graphviz step is the expensive part. Files for a view that has been
removed from `views.yaml` are deleted as orphans, which is how renames like
the `1-`…`7-` vision prefixes clean up after themselves. `--check` runs the
same comparison without writing anything and exits 1 on any stale or orphaned
diagram (for CI / pre-commit). `--no-svg` emits `.puml` only. Run `build.py`
first, because `render_diagrams.py` reads the generated XML and does not
rebuild it (`architecture/model/render_diagrams.py:1-30`).

`diagram-archimate` (the skill `render_diagrams.py` calls into for ArchiMate
notation) now fixes the layout direction for two relationship pairs rather
than leaving every edge to graphviz auto-layout: `Realization` and `Serving`
render with the PlantUML stdlib's `_Up` macro variant (the realizing/serving
element sits below what it realizes/serves, arrow pointing up), and
`Triggering`/`Flow` render `_Right` (process sequence reads left to right).
Every other relationship type is unaffected — this is a rendering hint only
(`REL_DIRECTION` in `model_to_puml.py`), not a change to source/target
semantics — see [Agent Skills & Workflows](agent-workflows.md).
