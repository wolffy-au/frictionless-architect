`platform/packages/portal`: the composition host that serves the platform
packages' UIs from one FastAPI app. It is not one of the six subsystems, and
it is explicitly not the central dashboard [ADR-0020](decision-log.md)
rejected earlier — it mounts each package's router and owns only page
chrome, navigation and the role landing page, never feature logic.

## Decision

[ADR-0020](decision-log.md) was updated in place on 2026-10-11
([GH #120](https://github.com/wolffy-au/frictionless-architect/issues/120))
to answer the composition question its 2026-09-26 revision had left open:
each subsystem ships its own UI, but something still has to compose them for
a user who isn't going subsystem-by-subsystem. The answer is `portal`, not a
seventh subsystem and not the single Vite/Backstage dashboard the original
(unratified) ADR-0020 had proposed. Each package keeps its own standalone
`app.py` for independent development; `portal` path-depends on them rather
than the other way around (`platform/packages/portal/README.md`).

## What it mounts

`src/portal/app.py` (75 lines) builds one `FastAPI` app and a tuple of
`MountedUi(path, title, role)` entries that drive the landing page:

| Path | UI | Package | Role |
|---|---|---|---|
| `/catalog` | Control conversion playground | `controls-compliance-catalog` | Compliance Officer / Auditor |
| `/settings/llm` | LLM settings | `llm-provider-config` | All roles |

`create_playground_router(prefix="/catalog")` and
`create_settings_router([...])` are the same router factories
`controls-compliance-catalog` and `llm-provider-config` use in their own
standalone apps — the portal registers the *catalog's* LLM component
(`controls_compliance_catalog.llm_client.COMPONENT_ID`) into the settings
router it mounts, so `/settings/llm` configures every registered package's
LLM usage from one place rather than per-package pages
(ADR-0034; see [LLM Provider Configuration](llm-provider-config.md)). The
landing page (`GET /`) groups `MOUNTED_UIS` by role and renders a plain
light/dark-aware HTML page with one `<section>` per role — no JS framework,
no build step.

Each mounted UI's own page JS is written prefix-relative (the
`llm-provider-config` `__PREFIX__`-substitution pattern), so the path column
above is the single place each one's mount point is actually decided. To add
a package's UI to the portal: include its router in `src/portal/app.py` and
add a `MountedUi` entry so the landing page lists it
(`platform/packages/portal/README.md` §"Mounted UIs").

The **Conversational Authoring UI** (`if-modelling-authoring-ui`, see
[Conversational Model Authoring](modelling-specification.md)) is not yet in
the `MOUNTED_UIS` tuple as of this build — it exists as a model-level
interface and an `ApplicationFunction` consumer
(`fn-conversational-authoring`) but the current `app.py` only wires
`/catalog` and `/settings/llm`. Not covered by current sources: a committed
plan or issue for mounting it.

## Run it

```bash
cd platform
poetry run uvicorn portal.app:app --reload
```

Then open `http://127.0.0.1:8000/` for the landing page.

## Model wiring

`sub-portal` is an `ApplicationComponent` composed into `sys-platform`,
explicitly not one of the six subsystems. Its interface, **Portal UI**
(`if-portal-ui`), is described as "a landing page listing each mounted
package UI by the role it serves, and the shared navigation into them". It
is realised by the `art-pkg-portal` `Artifact` (one of ten package
`Artifact`s in section E — see
[Architecture Model: Migration](architecture-model-migration.md)). See
[Architecture Model: Ecosystem](architecture-model-ecosystem.md) for the
element-level treatment, including the three `ApplicationInterface`s it
mounts (`if-catalog-playground`, `if-llm-settings-ui`,
`if-modelling-authoring-ui`).

See [Architecture Overview](architecture.md) §"UI composition" and
[LLM Provider Configuration](llm-provider-config.md) for the settings-router
mounting change this same ADR-0020 update made there.
