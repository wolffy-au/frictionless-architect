## Platform domain model

From `data-model.md`. Machine-readability is the first constraint — every
artifact is "executable or structured data (JSON/Markdown)"
(`data-model.md` §"Architecture Artifacts").

| Entity | Key attributes | Notes |
|---|---|---|
| Architecture Artifact | Content, Format, Version | Structured/executable representation of part of the architecture |
| **Architecture Decision Record (ADR)** | Title, Status, Date, Rationale, Decision, Consequences, Human Attestation | Requires a human cryptographic signature for `Approved`/`Superseded` (`data-model.md` §"Architecture Decision Record (ADR)") |
| Semantic System Model | Nodes: Microservices, Data Domains, CBS, Regulations; Edges: `uses`/`supports`/`governed by` | Graph-based (`data-model.md` §"Semantic System Model") |
| Critical Business Service (CBS) | Name, Description, Impact Tolerances (RTO/RPO), Mapped Technical Components, Associated Regulations | Must align with APRA CPS 230/234; tolerances are human-readable strings with units, e.g. "4 hours" (`specs/001-governance-platform/spec.md:24`) |
| Policy | Name, Type (CPS 230 / CPS 234 / OPA Rego), Content/Rules, Scope | Must be machine-readable and enforceable |

The [Platform Specification & API](platform-spec.md) `001` spec adds
**Break-Glass Exception** and **Audit Log Entry** as key entities.

### ADR lifecycle

`Draft → Under Review → Approved → Superseded`, a governed state machine
(`data-model.md` §"State Transitions"). Approved/Superseded require a mandatory
human cryptographic sign-off (`data-model.md` §"Validation Rules Summary"). This
is the kind of entity `TECHNICAL.md` says to model as an FSM with action-based
endpoints — see [Architecture Overview](architecture.md).

### Relationships

`data-model.md` §"Relationships": ADR `governs` Architecture Artifacts; ADR
`is_attested_by` a Human Architect; CBS `is_supported_by` Microservices and
`is_governed_by` Regulations and Policies; the Semantic System Model
`represents` Microservices/Data Domains/CBS/Regulations; Policy
`enforces_rules_on` CBS/Microservices/Data Domains.

## ArchiMate schema basis

The canonical schema files under `sample-data/schema/` are the published
**Open Group ArchiMate 3.1 Open Exchange Format** XSDs (`archimate3_Model.xsd`,
`archimate3_View.xsd`, `archimate3_Diagram.xsd`), used verbatim — author
"The Open Group ArchiMate Exchange Team", `version="3.1"`,
`targetNamespace="http://www.opengroup.org/xsd/archimate/3.1/"`
(`sample-data/schema/archimate3_View.xsd:1-9`). They define a `model` root
containing `elements`, `relationships`, `organizations`,
`propertyDefinitions`, and `views/diagrams`. Element and relationship types
are carried on the `xsi:type` attribute; view nodes carry required `x`/`y`
(`LocationGroup`) and `w`/`h` (`SizeGroup`) integer bounds plus `style`
(`sample-data/schema/archimate3_Diagram.xsd`, `LocationGroup`/`SizeGroup`).

> **Version mismatch worth knowing.** The XSDs are ArchiMate **3.1**, but the
> visualiser's sample parser pins the ArchiMate **3.0** namespace string
> `http://www.opengroup.org/xsd/archimate/3.0/`
> (`src/frictionless_architect/visualizer/sample_parser.py:10`). The XSDs
> also declare their *default* `xmlns` as the 3.0 URI while their
> `targetNamespace` is 3.1. Sample data authored against a strict 3.1
> namespace would not be matched by the parser's XPath queries.
> `specs/002-neo4j-schema-ui` variously calls the schema "ArchiMate 3" and
> "3.2"; neither matches the files.

## Schema-visualiser payload model

From `specs/002-neo4j-schema-ui/data-model.md` — the JSON contract the
visualiser serves (see [Visualizer Service](visualizer-service.md) and
[Platform Specification & API](platform-spec.md) for the endpoints):

| Type | Purpose |
|---|---|
| `ModelDefinition` | Top-level container: `identifier`, `name`, `namespace`, `schema_files`, `sample_source`, `loaded_at` |
| `ElementType` | Schema-defined node type (e.g. ValueStream) with `allowed_properties`, `source_file`, and linked `sample_instances` |
| `RelationshipType` | `directionality`, `source_restriction`, `target_restriction`, `source_file`; flagged if no sample instance exists |
| `SampleElement` | Concrete node from `Test Model Full.xml`; transitions `pending → verified` |
| `SampleRelationship` | Concrete edge; renders only if both endpoints exist |
| `ViewDiagram` / `DiagramNode` | Layout metadata (`x`/`y`/`width`/`height`, `style`) from `archimate3_View.xsd` |
| `VisualiserPayload` | Aggregated `model` + `elements` + `relationships` + `views` + `warnings` + `latency_ms` served to the front-end |

### Neo4j graph shape (as implemented)

The visualiser's Neo4j reader and the schema manager assume a specific graph
(`src/frictionless_architect/schema/manager.py:13-28`,
`src/frictionless_architect/visualizer/data_loader.py:49-91`):

- `(:Element {identifier, type, name, layer, documentation})` — unique on
  `identifier`, indexed on `type` and `layer`. A sanitised element-type label
  is added as a second label.
- `(:RelationshipFact {identifier, type, source_id, target_id})` plus a
  parallel `[:ARCHIMATE_RELATIONSHIP]` edge between the two `Element` nodes,
  and `[:SOURCE_ELEMENT]`/`[:TARGET_ELEMENT]` edges from the fact node.
- `(:View {identifier, name, viewpoint, viewpointRef})`,
  `(:Diagram)`, `(:Viewpoint)`, `(:SchemaVersion {name, applied_at})`.
- `[:INCLUDES]`, `[:HAS_RELATIONSHIP]`, `[:REPRESENTS_VIEW]`, `[:HAS_NODE]`,
  `[:HAS_CONNECTION]` wire views and diagrams to elements and relationship facts.

### Validation / audit rules

`SchemaManager` refuses to ingest a relationship whose source or target
`Element` is missing (`src/frictionless_architect/schema/manager.py:132-141`),
and `run_audit_checks()` reports relationship facts with a missing endpoint and
"orphan" views that include zero elements or zero relationships
(`src/frictionless_architect/schema/manager.py:268-297`).
