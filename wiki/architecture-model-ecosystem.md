Section B of `elements.yaml`: the application-layer ecosystem
(`architecture/model/elements.yaml:14`). Part of the [Architecture Model](architecture-model.md), which covers the files, schema and content sections.

The platform `Grouping` (`sys-platform`, `props: c4=system`), its six
subsystems (`ApplicationComponent`s → C4 containers), five shared stores
(`DataObject`s → C4 databases), six business roles (→ C4 persons), and seven
external systems (`ApplicationComponent`s outside the grouping → C4 external
systems) (`architecture/model/elements.yaml:878-1054`). Three further
`ApplicationComponent`s sit beside them without being subsystems:
`sub-schema-visualizer`, `sub-llm-provider-config` ("LLM Provider
Configuration", since ADR-0034), and `sub-portal` ("Portal", since the
ADR-0020 update of 2026-10-11, GH #120). `sub-llm-provider-config` resolves
provider, model and credential for LLM calls. It is composed into
`sys-platform`, has an `Association` to the `ext-llm` external system, and
is realised by `art-pkg-llm-provider-config`; there is deliberately no
`Serving` edge to its consumers, since consumption is a path dependency, not
a runtime call
(`architecture/model/elements.yaml:942-950`, `architecture/model/relationships.yaml:772-786`).
It appears in the Artefact Flow — Controls & OSCAL and Packaging views
(`architecture/model/views.yaml`).

`sub-portal` "hosts the platform packages' UIs from one app: mounts each
package's router and owns only page chrome, navigation and the role landing
page, never feature logic" — explicitly not one of the six subsystems and not
a central dashboard (`architecture/model/elements.yaml` — `sub-portal` desc).
Its interface, **Portal UI** (`if-portal-ui`), is "a landing page listing
each mounted package UI by the role it serves, and the shared navigation
into them". It is realised by the `art-pkg-portal` Artifact. See
[Portal](portal.md) for the package itself.

This is the
decomposition [ADR-0011](decision-log.md) adopts in place of the old
eight-component grouping; [Architecture Overview](architecture.md)
§"Subsystem → package mapping" gives the package each subsystem becomes. Views: `Subsystems & Capabilities` (a
standard `layered` view, rendered to `layered/subsystem-capabilities`; see
[Architecture Views & Diagrams](architecture-diagrams.md)) and the generated C4 context + container ([ADR-0009](decision-log.md)).

Every subsystem `Realization`-links to a section-A capability ([Skeleton](architecture-model-skeleton.md)), tying the C4
view back to the skeleton (`architecture/model/relationships.yaml:419-428`).
Shared stores (`architecture/model/elements.yaml:967-991`): OSCAL Repository
(`store-oscal`), Pattern & Blueprint Repository (`store-patterns`),
Architecture Knowledge Graph (`store-akg`, "one graph store, two planes:
Architecture Intent and Current-State Digital Twin"), Framework Pack Library
(`store-frameworks`), Forensic Audit Ledger (`store-ledger`). The seven external
systems (`architecture/model/elements.yaml:1018-1054`) are Source Control, CI/CD Pipeline
(which now "runs the controls enforcement gate inline"),
Cloud & Infrastructure Platforms, IT Service Management / Backlog, LLM
Provider, RFP / Vendor Submissions, and `ext-trestle`
("compliance-trestle"), added per [ADR-0030](decision-log.md). Trestle's
`desc` calls it a "third-party Python library/CLI dependency, not vendored
source" that "Performs the Trestle Markdown <-> OSCAL round-trip behind
fn-oscal-conversion". The platform invokes Trestle rather than passively exchanging data
with it, so its edges are `Serving`, not the `Flow`/`Access` used for the
peer systems. It serves `fn-oscal-conversion` (the Markdown ↔ OSCAL
round-trip), `fn-baseline-tailoring` (profile authoring) and
`fn-oscal-profile-resolve` (profile resolution). The LLM
Provider now also serves `fn-ai-markdown-conversion`, so its `desc` covers
converting policy/standard documents alongside its drafting uses
(`architecture/model/relationships.yaml:446-451`).

The former `ext-regsources` ("Regulatory Content Sources") external system
has been **removed**. It implied a system integration with upstream
regulators that does not exist. Upstream regulatory text now enters as a
plain document artefact, `do-regulatory-standard`, on the same footing as
a custom policy document (see "Controls & OSCAL" in
[Architecture Model: Artefact Flow](architecture-model-artefact-flow.md)). See
[OSCAL Compliance Content](oscal-compliance.md) for the vendored OSCAL
reference content the golden datasets come from.

The subsystem `includes` free-text property was removed — the same
decomposition is carried by the section-C `ApplicationFunction`s ([Artefact Flow](architecture-model-artefact-flow.md)) and their
`Assignment` edges ([ADR-0027](decision-log.md) §"Consequences").

The six business roles (`architecture/model/elements.yaml:992-1016`) are now
also `Assignment`-linked to the section-A BusinessFunctions they perform. For
example, the Compliance Officer performs Policy-to-OSCAL Conversion. That
nesting is what the Controls & Compliance Catalog view draws; see
[Skeleton](architecture-model-skeleton.md).

**Context tagging (GH #105/#108).** Every section-B element now carries a
`context:` property — `platform` for the shared kernel, or the owning
package's name for a subsystem-specific element — so a view's `context:`
scoping key (see [Architecture Model](architecture-model.md) §"Schema") can
draw `include_types` sweeps from one package at a time. See
[Architecture Model: Context-Level Viewpoints & Bounded Contexts](architecture-model-contexts.md). The tags are now explicit on the interfaces and
collaboration elements too: `if-catalog-playground` is
`controls-compliance-catalog`, `if-llm-settings-ui` `llm-provider-config`,
`if-modelling-authoring-ui`, `bc-model-collaboration` and
`bi-collaborative-modelling` `modelling-specification`
(`architecture/model/elements.yaml`). The business-role descriptions that cite
`(GH #45)` are now double-quoted, because an unquoted ` #` starts a YAML
comment and would truncate the text in every generated diagram
(`architecture/model/README.md` §"Schema").

**New interfaces (2026-10).** Beyond `if-catalog-ui` and
`if-twin-read-path`, three more `ApplicationInterface`s were added:
**Control Conversion Playground** (`if-catalog-playground`) — a dev-tool
interface that runs one control through both the AI-candidate and
deterministic conversion paths for side-by-side comparison, mounted by the
portal at `/catalog`; **LLM Settings UI** (`if-llm-settings-ui`) — the
mountable settings page/API for the global LLM default and per-component
overrides, mounted by the portal at `/settings/llm` and by each consuming
package's own standalone app; and **Conversational Authoring UI**
(`if-modelling-authoring-ui`) — the human-facing split-screen interface (and
its `/authoring` JSON API) for `sub-modelling`'s conversational model
authoring. Since ADR-0039 (GH #68/#138), `if-modelling-authoring-ui` is
shared by a second function: `sub-library`'s new `fn-solution-modelling`
(the Solution Architect's conversational counterpart to `fn-solution-compose`,
editing a Solution Design rather than the candidate-architecture graph) gets
its own `Serving` edge to the same interface, mirroring
`fn-conversational-authoring`'s existing one, rather than a new interface or
a package dependency between `sub-library` and `sub-modelling`. See
[Portal](portal.md), [Architecture Model: Skeleton](architecture-model-skeleton.md)
and [Conversational Model Authoring](modelling-specification.md).

A 2026-09-27 pass (GH #55 follow-up) added `sub-catalog`'s own
`ApplicationInterface`, **Compliance Catalog UI** (`if-catalog-ui`) — the
human-facing surface where the Compliance Officer/Auditor uploads
policy/standard documents, reviews prose-quality feedback, and tracks
Catalog/Profile status (`Composition` from `sub-catalog`; `Serving` to
`role-compliance`, labelled "upload, feedback & status UI"). The same pass
resolved where the schema-visualiser UI itself lives: `sub-schema-visualizer`
gets a direct `Serving` edge to `role-ea`, composing into that role's
existing journey alongside `sub-library`/`sub-governance`/`sub-assurance`
rather than becoming a seventh subsystem or a standalone dashboard
(ADR-0005 + [ADR-0020](decision-log.md)). Both are recorded in
[Architecture Model](architecture-model.md) §"Technology (section F)"
alongside the `TechnologyFunction` that actually performs the
