How the YAML model is built into the ArchiMate exchange file, and how the vendored IT4IT model
is merged in at build time. Part of the [Architecture Model](architecture-model.md), which covers
the files, schema and content sections.

## Build pipeline

The package finds the model through `FRICTIONLESS_MODEL_DIR`, defaulting to this
directory, so another repo can install it and point it at its own model
(`architecture/model/README.md` §"Architecture model"; ADR-0045; see
[Conversational Model Authoring](modelling-specification.md#using-it-against-another-model-adr-0045)).

The root `build.py` dispatches to the package CLI, which owns the YAML-to-XML
build path (`architecture/model/README.md` §"Architecture model";
`architecture/model/build.py:1-55`;
`platform/packages/modelling-specification/src/modelling_specification/cli.py:18-36`):

1. The CLI loads and merges first-party YAML with optional vendored and
   generated layers (`build_model`), then assembles and validates the model
   (`_assemble`)
   (`platform/packages/modelling-specification/src/modelling_specification/model_io.py:1119-1173`).
2. Stable identifiers are derived from element ids and relationship fields via
   `det_id`, so repeated builds do not churn the exchange model
   (`platform/packages/modelling-specification/src/modelling_specification/model_io.py:218-227,326-397`).
3. Motivation and viewpoint conventions are checked during model assembly
   (`check_motivation_conventions`, `check_view_coverage`)
   (`platform/packages/modelling-specification/src/modelling_specification/model_io.py:489-540`).
   `add_views` now hands each view to a `_build_view` helper (nodes, neighbours,
   connections, viewpoint check, layout), with no change in behaviour
   (`platform/packages/modelling-specification/src/modelling_specification/model_io.py:824-968`).

The loader rejects null YAML values rather than allowing truncated flow-style
entries through (`_check_null_keys`), and writes the XML only after
successful assembly (`write_and_validate`)
(`platform/packages/modelling-specification/src/modelling_specification/model_io.py:262-283,1834-1849`).
`env_dir`, which resolves `FRICTIONLESS_MODEL_DIR` below, now also rejects a
blank or NUL-bearing value and canonicalises the path with
`os.path.realpath` rather than `Path.resolve()` — hardening against Snyk's
Path Traversal findings, though Snyk does not treat `env_dir` itself as a
sanitiser and still reports them
(`platform/packages/modelling-specification/src/modelling_specification/model_io.py:54-64`).

## The vendored-model sweep, and why `sample-azure` is excluded from it

The merge step does not hardcode `third_party/it4it` by name: `VENDORED_MODELS`
globs every `third_party/*/elements.yaml` and merges each match in, so a
second vendored reference model needs no code change to join the merge
(`platform/packages/modelling-specification/src/modelling_specification/model_io.py:92,111-117`).
A 2026-11-11 fix (GH follow-up) carved out one exception:
`third_party/sample-azure` also carries its own `elements.yaml`, but for the
opposite reason IT4IT does — [ADR-0045](decision-log-0030-onward.md) lets a
*different* repo install this package and point `FRICTIONLESS_MODEL_DIR`
straight at its own model directory, and `sample-azure` is exactly that: a
standalone demo Azure app meant to be built by pointing at it directly, not
swept into this repo's own root model. The generic glob couldn't tell the two
cases apart, so it pulled `sample-azure`'s elements into the platform model
(and its `diagrams/`) whenever the submodule happened to be checked out
locally. `_STANDALONE_THIRD_PARTY_MODELS = {"sample-azure"}` now excludes it
from the default sweep by name; it is still buildable/renderable on its own
by `cd`-ing into it, or reachable here by pointing
`FRICTIONLESS_THIRD_PARTY_DIR` at a directory that includes it under another
name.

## IT4IT alignment — vendored as its own repo, imported at build time

The IT4IT 3.0 value-stream skeleton used to live inline in this repo's own
`elements.yaml`/`relationships.yaml`, tagged `props: {source: it4it}` so it
could be filtered from the platform's own model. [ADR-0029](decision-log-ui-visualiser-model.md)
moved it out: it now lives in `third_party/it4it`, a **git submodule**
pointing at `wolffy-au/frictionless-it4it` on GitHub, in the same
`elements.yaml` / `relationships.yaml` / `views.yaml` schema this repo uses.
The model loader loads it alongside the first-party YAML and merges both into the
**same** `det_id()` / `NS` hashing pass — there is no separate build step, no
separate `.xml`, and no ID-reconciliation machinery. Every IT4IT element and
relationship keeps the `it4it-` id prefix it always had, and that prefix
alone is what keeps the merged id space collision-free
(`platform/packages/modelling-specification/src/modelling_specification/model_io.py:81-105,192,218-227`).

This is a decision about *packaging*, not content — nothing about the IT4IT
data itself changed:

- **Value-stream skeleton** (`third_party/it4it/elements.yaml`) — a root
  wrapper `ValueStream` (`it4it-vs-root`, "IT4IT: Value Streams")
  `Composition`-linking its 7 IT4IT value streams (Explore, Evaluate,
  Integrate, Deploy, Release, Operate, Consume) and `Realization`-linking to
  one `Outcome` ("IT4IT: Digital Product"); each stream in turn
  `Composition`-links its stages (28 total). The streams form a **`Flow`
  network, not a linear pipeline** — several stream pairs flow both ways in
  the source model, preserved as-is (`third_party/it4it/relationships.yaml`).
- **42 IT4IT capabilities** — 24 reachable from a stage via the source
  model's own `DataObject → Resource → Capability` chain, collapsed into a
  single **derived** `Capability --Serving--> Stage` edge per reachable pair
  (tagged `props: {derived: "true"}`, labelled `<<derived>>`), plus 18 more
  capabilities the derivation chain doesn't reach, carried for completeness.
  This is an *explicit* relationship pre-computed once in the vendored YAML
  and merged in like any other — not the same mechanism as `views.yaml`'s
  2026-11-11 **view-level** `derived: true` flag, which overlays
  relationships at render time, from nothing stored in YAML at all. Both use
  `<<derived>>` because both represent an ArchiMate derived relationship; see
  [Architecture Model](architecture-model.md) §"Schema rules" for the newer
  one.
- **Bridge to the platform's own capabilities** — 9 `Association` edges,
  tagged `props: {source: it4it-alignment}`, are the one piece of IT4IT-
  referencing content that **stays first-party**, in this repo's own
  `relationships.yaml` "D. IT4IT TOUCHPOINTS" section — their source
  endpoint is always one of this platform's own `cap-*` capabilities, e.g.
  `cap-digital-twin` ↔ IT4IT Configuration Management / Architecture
  Management, `cap-control-plane` ↔ IT4IT Product Development,
  `cap-forensic-ledger` ↔ IT4IT Compliance Management
  (`architecture/model/relationships.yaml` §"D. IT4IT TOUCHPOINTS").

`third_party/it4it` also carries its own `views.yaml` and `diagrams/vision/`
(the same 4 pure-IT4IT views described below, rendered by this repo's
`render_diagrams.py` into that vendored diagrams directory) — a view whose
content is 100% `it4it-*` elements is vendored alongside the data it draws
on, the same reasoning that vendored the elements/relationships. The one
exception is the capability-bridges touchpoint view, which stays here since
it spans both models. Deliberately **excluded from every other view** in the
model, so IT4IT elements never pollute a platform-only diagram.

If IT4IT is ever consumed via its own independently-generated `.xml` (its own
`build.py` / `NS`) instead of raw YAML, this merged-hashing approach no
longer holds — that would need its own ADR ([ADR-0029](decision-log-ui-visualiser-model.md)
§"Consequences").
