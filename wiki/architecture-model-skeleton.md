This page covers Section A of `elements.yaml`, which the file calls "the load-bearing
skeleton" (`architecture/model/elements.yaml:12-13`). Section A holds the motivation, strategy and
business layers. It is part of the [Architecture Model](architecture-model.md), which covers the files,
schema, build pipeline and IT4IT alignment.

Section A is the subset that stays true however the component boundaries finally
land ([ADR-0010](architecture.md)). It is **decomposition input, not the final
architecture**. Even so, it carries a full TOGAF ADM Phase A vision, and since
PR #62 it also carries a Phase B business layer. In brief:

- **Motivation:** stakeholders and assessments drive four outcomes, which
  realize one goal.
- **Strategy:** capabilities, courses of action and resources, plus four
  value streams (one per outcome).
- **Business:** 15 processes grouped under 9 business functions, and the business
  objects they read and write.

## Motivation

### Stakeholders, drivers and assessments

**Stakeholders.** There are five (`architecture/model/elements.yaml:59-93`):

- Executive Leadership & Board (`stk-exec`)
- Prudential Regulator (APRA) (`stk-regulator`)
- Enterprise Architecture Function (`stk-architecture`)
- Delivery Organisation (`stk-delivery`)
- Risk & Compliance Function (`stk-risk-compliance`)

Each stakeholder is `Association`-linked to the driver(s) it holds
(`architecture/model/relationships.yaml:90-103`). Each is also linked to the value
stream(s) that deliver value to it (see "Value streams" below).

**Drivers.** There are four, and they say why the platform exists (`architecture/model/elements.yaml:27-57`):

- Market Agility & Competitive Pressure
- Regulatory Resiliency & Social License
- Systemic Sustainability & Complexity Management
- Human-to-Machine Operational Scaling

**Assessments.** There is one per driver, each a finding that makes its driver urgent
(`architecture/model/elements.yaml:95-120`):

- time-to-market falling behind AI-native competitors
- human review unable to keep pace with AI-speed delivery
- architectural drift accumulating as unmanaged risk
- manual compliance evidence that is too slow and error-prone

Each Assessment's `name` is written in its stakeholder's own vocabulary, for
example "risking market share" rather than "manual architecture governance". This
authoring convention is documented in the header comment and reviewed by eye,
not mechanically checked (`architecture/model/elements.yaml:17-25`).

### Goal and outcomes — the motivation spine

The goal is *Frictionless Architecture & Governance at Machine Speed*
(`goal-frictionless-architecture`). Four outcomes realize it
(`architecture/model/elements.yaml:122-164`):

| Outcome (`id`) | Answers assessment | Realized by requirements | Realized by value stream |
|---|---|---|---|
| Approved Change Reaches Production at AI Speed (`outcome-change-at-ai-speed`) | time-to-market | auto spec generation, reusable architecture | Governed Architecture Delivery |
| Compliance Proven Before Release (`outcome-compliance-before-release`) | manual compliance | regulatory mapping, control catalog, pre-deploy gate | Obligation to Evidence |
| Accountable, Auditable Automation (`outcome-accountable-automation`) | review bottleneck | human sign-off, immutable audit ledger | Exception to Decision |
| Drift Detected and Reconciled Continuously (`outcome-drift-reconciled`) | drift debt | authoritative twin, continuous reconciliation | Drift to Remediation |

(`architecture/model/relationships.yaml:104-132`.) The spine is `driver
→ assessment → outcome → goal`: each driver `Influence`s its assessment,
each assessment `Influence`s the outcome that answers it, and each outcome
`Realization`-links to the goal. Each requirement and each value stream
realizes **exactly one** outcome.

`outcome-drift-reconciled` replaces the former single outcome, "Architecture
as Executable Intelligence". That phrase now lives in the `desc` of
`vs-governed-delivery` ("Architecture as executable intelligence, applied to
delivery") (`architecture/model/elements.yaml:439-446`).

**Edges that are deliberately absent.** The model has no Assessment → Goal,
Assessment → Requirement, Driver → Requirement or Requirement → Goal edge. Each one
would make an existing edge *derived*. An Assessment → Requirement influence, for
example, would make Assessment → Outcome derivable through the requirement. The
Stakeholder view, whose viewpoint admits no Requirement, needs that
Assessment → Outcome edge to show which concern each outcome answers
(`architecture/model/relationships.yaml:117-141`; `architecture/model/README.md`
§"Model contents").

`build.py`'s `check_motivation_conventions` catches the structural mistakes
here: "a Driver bypassing its Assessment, a derived Constraint/Requirement->Goal
edge" (`architecture/model/elements.yaml:22-25`). The checker itself lives in
`build.py`, which is not a source of this topic; see
[Architecture Model](architecture-model.md).

### Principles, constraints and requirements

**Principles.** There are three, all constitution-level (`architecture/model/elements.yaml:166-184`):

- Deterministic Human Accountability ("AI is advisory; the specification is
  deterministic; a human holds sign-off")
- Forensic Auditability
- Policy as Code

**Constraints.** There are four. Each is worded as a design limit on *this platform's* own
architecture, not as a summary of a regulation (`architecture/model/elements.yaml:186-223`):

- No Retrospective Compliance (APRA CPS 230/234)
- No Autonomous Self-Validation of Agentic Decisions
- Privacy Mapping Is Mandatory, Not an Out-of-Band Check
- Governed State Confined to Approved Sovereignty Boundary

**One edge each.** Each principle and constraint `Influence`s the **one**
requirement that most directly operationalises it. That keeps the Motivation view
readable. They reach outcomes and the goal only through that requirement
(`architecture/model/relationships.yaml:143-157`):

| Source | Influences |
|---|---|
| Deterministic Human Accountability | `req-human-signoff` |
| Forensic Auditability | `req-immutable-audit-ledger` |
| Policy as Code | `req-control-catalog` |
| No Retrospective Compliance | `req-pre-deploy-gate` |
| No Autonomous Self-Validation | `req-human-signoff` |
| Privacy Mapping Is Mandatory | `req-regulatory-mapping` |
| Governed State Confined to Sovereignty Boundary | `req-authoritative-twin` |

Three requirements (spec generation, reusable architecture and continuous
reconciliation) carry no such influence. They are justified by the outcome they
realize instead.

**Functional requirements.** There are nine, and each is a component contract
(`architecture/model/elements.yaml:225-313`):

- automated specification generation from the graph
- automated regulatory-obligation mapping
- pre-deployment compliance-gate enforcement
- continuous as-built vs. as-designed reconciliation
- mandatory human sign-off for non-standard changes
- a maintained machine-readable control catalog
- a curated reusable architecture library
- an authoritative digital twin of system state
- an immutable forensic audit ledger

([ADR-0027](architecture.md); `architecture/model/elements.yaml:315-381`).
Every capability realizes at least one requirement
(`architecture/model/relationships.yaml:15-45`), and each is `Assignment`-linked
from the resource that equips it (`architecture/model/relationships.yaml:47-57`):

| Capability (`id`) | Realizes | Resource |
|---|---|---|
| Architecture Knowledge Management (`cap-digital-twin`) | `req-authoritative-twin` | Architecture Knowledge Graph |
| Executable Specification Generation (`cap-spec-engine`) | `req-auto-spec-generation` | Architecture Knowledge Graph |
| Agentic Development Supervision (`cap-control-plane`) | `req-pre-deploy-gate` | AI Delivery Agents |
| Forensic Audit Recording (`cap-forensic-ledger`) | `req-immutable-audit-ledger` | Accumulated Evidence Record |
| Architectural Drift Detection & Reconciliation (`cap-drift-dashboard`) | `req-continuous-reconciliation` | Architecture Knowledge Graph |
| Human Oversight & Approval (`cap-human-approval-workflow`) | `req-human-signoff` | Enterprise Architecture Practice |
| Control & Obligation Management (`cap-control-catalog`) | `req-regulatory-mapping`, `req-control-catalog` | OSCAL Control Content |
| Reusable Architecture Curation (`cap-reusable-architecture`) | `req-reusable-architecture` | Enterprise Architecture Practice |

The fifth resource, **Accumulated Evidence Record** (`res-evidence-record`), is new.
It is "the growing, append-only body of recorded agent" actions and decisions
behind forensic audit recording (`architecture/model/elements.yaml:425-429`).

Eight `Capability → Capability` `Serving` edges record the dependency order
between capabilities (`architecture/model/relationships.yaml:205-216`):

- Knowledge Management serves Spec Generation ("authoritative graph") and
  Drift Detection ("as-designed intent").
- Reusable Architecture serves Spec Generation.
- Control & Obligation Management serves Reusable Architecture ("control
  mappings") and Development Supervision ("expected controls").
- Spec Generation serves Development Supervision.
- Forensic Audit Recording and Development Supervision both serve Human
  Oversight. The Development Supervision edge, labelled "escalations", is new.

### Courses of action

There are three courses of action (`architecture/model/elements.yaml:383-407`):

- Shift Governance Into the Pipeline (`coa-executable-governance`), realized
  by five capabilities
- Operate a Living Architecture Twin (`coa-living-twin`)
- Curate Reuse Before Build (`coa-reuse-first`)

Each course of action `Influence`s the goal (`architecture/model/relationships.yaml:47-69`). Each also
`Serving`-links to the value streams it drives. A `CourseOfAction →
ValueStream` `Realization` is not a legal ArchiMate 3.2 pair, but `Serving` is.
The links are (`architecture/model/relationships.yaml:70-80`):

- Reuse-First → Governed Delivery
- Executable Governance → Governed Delivery, Obligation to Evidence and
  Exception to Decision
- Living Twin → Drift to Remediation

### Value streams — one per outcome

[ADR-0033](architecture.md) replaced the single six-stage "Governed Architecture
Delivery" stream with **four streams, one per outcome**, organised by who
*receives* the value. That gives 15 `ValueStream` elements: 4 streams and 11
stages (`architecture/model/elements.yaml:431-539`). Each stream realizes its
outcome, is `Association`-linked to its value recipients with a labelled edge,
and is a `Composition` of its stages. Each stage is `Serving`-linked from the
capability that enables it (`architecture/model/relationships.yaml:81-88`,
`159-184`):

| Stream | Recipients | Stages (served by) |
|---|---|---|
| Governed Architecture Delivery | Delivery Organisation ("compliant releases at speed"), Executive ("time to market") | Establish Reuse Baseline (Reusable Architecture) → Specify the Change (Spec Generation) → Build Under Supervision (Development Supervision) → Release to Production (Development Supervision) |
| Obligation to Evidence | Risk & Compliance ("provable compliance"), Regulator ("evidence before release") | Establish Control Baseline (Control & Obligation Mgmt) → Prove Compliance (Development Supervision) |
| Exception to Decision | Executive ("accountable automation"), Risk & Compliance ("examinable decisions") | Escalate Non-Standard Change (Development Supervision) → Decide & Sign Off (Human Oversight) → Record as Evidence (Forensic Audit Recording) |
| Drift to Remediation | Enterprise Architecture ("sustained coherence") | Observe As-Built State (Knowledge Management) → Reconcile & Remediate (Drift Detection) |

Stages *move* between streams rather than being duplicated
([ADR-0033](architecture.md)):

- "Prove Compliance" now belongs to Obligation to Evidence, and "Reconcile &
  Remediate" to Drift to Remediation.
- The old control-and-reuse baseline splits into a reuse baseline and a control
  baseline.
- "Release & Attest" becomes "Release to Production".

**Hand-offs between streams** connect the stages across streams
(`architecture/model/relationships.yaml:185-204`):

```text
Build ─Triggering▶ Prove ─Triggering▶ Release ─Triggering▶ Observe
                     │                   ▲
                     │ Triggering        │ Flow "approval"
                     │ "not              │
                     ▼ deterministically │
                  Escalate ─▶ Sign Off ──┘ ─▶ Record
                     validated"
Reconcile ─Flow "drift remediation re-enters"▶ Specify
```

The sign-off returns to Release as a `Flow`, not a second `Triggering`. A
Triggering there would make Prove → Release derived through the escalation path.

## Business layer

### Processes and functions

There are 15 `BusinessProcess`es, grouped by `Composition` under 9 `BusinessFunction`s
(`architecture/model/elements.yaml:541-729`;
`architecture/model/relationships.yaml:259-341`). Roles are `Assignment`-linked
to the *function* they perform, not to individual processes:

| Function | Processes | Assigned role |
|---|---|---|
| Policy-to-OSCAL Conversion | Policy & Standards Authoring, OSCAL Catalog Generation, Control Baseline Tailoring, OSCAL Profile Resolution | Compliance Officer / Auditor |
| Pattern & Blueprint Traceability | Pattern Control Traceability Mapping, Blueprint Control Enablement Mapping | Enterprise Architect |
| Solution Design | Solution Design Composition | Solution Architect |
| Architecture Strategy | Target State Definition | Enterprise Architect |
| Agentic Delivery Execution | Deterministic Spec Generation, Agentic Development Execution | — |
| Release Controls Enforcement | Automated CICD Gate Execution | — |
| Release Management | Production Release | — |
| Controls Effectiveness Assurance | Controls Effectiveness Monitoring | Platform Operations (BAU) |
| Drift Management | Architecture Reconciliation, Drift Review & Triage | Enterprise Architect ("approves architectural drift") |

Several processes are new or have been renamed:

- **New:** Target State Definition, Solution Design Composition, Control Baseline
  Tailoring and OSCAL Profile Resolution.
- **Renamed:** Current State Discovery is now **Architecture Reconciliation**,
  and the drift gate is now **Drift Review & Triage**. In Drift Review & Triage,
  an Enterprise Architect approves architectural drift.
- **Narrowed:** OSCAL Catalog Generation no longer produces Profiles. Every
  Profile, "including a published baseline such as NIST SP 800-53B", is tailored
  by a human in Control Baseline Tailoring
  (`architecture/model/elements.yaml:683-706`).

A header note flags that the `bfn-*` functions group processes by lifecycle.
They "could — and arguably should — be re-cut to align with the journeys of the
section-B roles" (`architecture/model/elements.yaml:605-611`).

**The choreography.** The processes form one connected chain, with Triggering
hand-offs unless marked `Flow` (`architecture/model/relationships.yaml:235-341`):

```text
Policy Authoring → OSCAL Catalog Generation → Baseline Tailoring
  → Profile Resolution → Pattern Traceability → Blueprint Traceability
  → Solution Design Composition → Spec Generation → Agentic Development
  → CICD Gate → Production Release → Architecture Reconciliation
  → Drift Review & Triage
Baseline Tailoring ─Flow▶ Controls Effectiveness Monitoring
Target State Definition ─Flow "target state reconciled against"▶ Architecture Reconciliation
```

All 15 processes `Realization`-link to a capability. Control & Obligation
Management is realized by five of them: the four Policy-to-OSCAL processes and
Controls Effectiveness Monitoring (`architecture/model/relationships.yaml:217-234`,
`399`).

### Business objects

There are 22 `BusinessObject`s, the business-layer counterparts of section C's artefacts
(`architecture/model/elements.yaml:731-877`). Most carry a `Realization` link
back to their `DataObject`; see
[Artefact Flow](architecture-model-artefact-flow.md). They fall into two groups.

- **Controls journey.** The first group is Regulatory Standard (a `Specialization`
  of Policy / Standard Document), Policy / Standard Document, OSCAL Catalog and
  OSCAL Profile. Next comes the **Resolved OSCAL Profile Catalog**
  (`bo-oscal-resolved-catalog`), "the operative control baseline for downstream
  use". It is a `Specialization` of OSCAL Catalog and `Association`-linked to
  the Profile whose selection it fulfils. After that come Architecture Pattern,
  Implementation Blueprint, OSCAL Component Definition, Solution Component,
  Solution Design, OSCAL SSP, OSCAL Assessment Plan, OSCAL Assessment Results
  (specialized by Release Gate Decision and Control Effectiveness Evidence),
  and **OSCAL Plan of Action & Milestones**. Patterns map to, and blueprints
  check enablement against, the *resolved catalog* rather than the raw Profile.
  A profile only selects and tailors controls, while the resolved catalog
  carries the effective control content
  (`architecture/model/relationships.yaml:299-314`).
- **Architecture strategy and drift.** The second group is Current State,
  Target State and Transition State Architecture, Architecture Roadmap, Drift
  Finding, and the Architecture Conformance Register. The Architecture
  Conformance Register is "the system of record for every drift finding and its
  triage status"; findings approved for remediation are raised as ITSM work
  items, but "the register itself is not a backlog"
  (`architecture/model/elements.yaml:819-877`).

**The `archimate-analogue` prop.** Five of these objects carry it:

| Object | `archimate-analogue` |
|---|---|
| Current State Architecture | Baseline Plateau |
| Target State Architecture | Target Plateau |
| Transition State Architecture | Transition Plateau |
| Architecture Roadmap | Plateau sequence with Work Packages and Implementation Events |
| Drift Finding | Gap |

The prop exists because the *content* of these objects, in the managed estate's
model, is an Implementation & Migration concept. Keeping it as a tag leaves this
model's own Plateaus free to mean states of the platform itself
(`architecture/model/README.md` §"Schema").

**Reconciling against the Transition State.** Architecture Reconciliation reconciles
the Current State against the **Transition State in effect**, "so gaps planned for later
states are not flagged as drift". It records findings in the Conformance
Register, and Drift Review & Triage updates their status there
(`architecture/model/elements.yaml:574-590`;
`architecture/model/relationships.yaml:336-349`).

**Where the POA&M sits.** Target State Definition takes remediation milestones
from the OSCAL POA&M. The CICD gate and effectiveness monitoring both write
control deficiencies into the POA&M
(`architecture/model/relationships.yaml:339-356`).
