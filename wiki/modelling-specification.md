Subsystem 6 of the platform, `platform/packages/modelling-specification`: a
conversational agent (GH #108) that turns a natural-language request from an
Enterprise Architect into a validated candidate-architecture delta,
live-rendered on accept. The package also now holds the deterministic model
build/render/validate logic that root's scripts and the `model-archimate`
skill used to carry themselves. See [Architecture Model](architecture-model.md)
for the model elements this feature adds, and [Decision Log](decision-log-0030-onward.md)
for ADR-0037, the record of its eight load-bearing design decisions.

**Renamed, and a sibling distinguished (ADR-0039, GH #68/#138, 2026-10-24).**
The process and function, once shared by the Enterprise and Solution Architect,
are renamed **"Conversational Candidate Architecture Authoring"** (ids unchanged:
`process-conversational-authoring` / `fn-conversational-authoring`) and scoped to
the Enterprise Architect alone, editing `do-candidate-arch`. The unused Solution
Architect `Assignment` is dropped for a distinct sibling, `fn-solution-modelling`,
which edits a `do-solution-design` instead. See [Architecture Decision Log: ADR-0030 onward](decision-log-0030-onward.md) and
[Architecture Model: Skeleton](architecture-model-skeleton.md) for both.

## Why the code lives here

[ADR-0037](decision-log-0030-onward.md) (Proposed 2026-10-10) decided the package's
shape and three related questions `plan.md`'s Constitution Check flagged as
load-bearing:

- **Package location.** A new `platform/packages/modelling-specification`
  sibling package, matching the `controls-compliance-catalog` pattern
  (ADR-0002, ADR-0011) — not `src/frictionless_architect/`, which is the
  pre-migration flat layout.
- **One implementation, three callers.** `architecture/model/build.py`'s
  YAML load/merge/validate logic and `render_diagrams.py`'s view-render logic
  moved into this package as `model_io.py` (1702 lines) and `rendering.py`
  (461 lines). Root's `build.py`, `render_diagrams.py` and the
  `model-archimate` skill's `validate.py` are now thin wrappers that shell
  into the platform venv's CLI — `poetry run --directory platform python -m
  modelling_specification.cli build|render|validate`
  (`platform/packages/modelling-specification/src/modelling_specification/cli.py`). This keeps ADR-0001's
  root-never-imports-a-platform-package boundary: root only shells out, as
  it always did, just uniformly across all three entry points now instead of
  carrying its own copy of the logic.
- **Enterprise Convention Rules move to data.** A new
  `architecture/model/conventions.yaml` holds organisation-specific
  authoring rules (naming/altitude conventions, interposed-element shapes)
  as inspectable, editable YAML, composed under `store-frameworks`
  alongside `do-metamodel`. The fixed ArchiMate 3.2 metamodel rules
  themselves stay sourced from pyArchimate — only the enterprise/domain
  layer on top is externally configurable
  (`platform/packages/modelling-specification/src/modelling_specification/validation/conventions.py`).
- **Overrides become ADR stubs, not ledger entries.** When an architect
  overrides a flagged objection, the override is recorded as an
  auto-drafted `Status: Proposed` ADR stub under `docs/adr/`
  (`platform/packages/modelling-specification/src/modelling_specification/authoring/overrides.py`), not appended to `store-ledger` — an override
  is an architecture-governance decision, not controls/compliance evidence,
  and the existing `adr-auditor` sweep already picks up exactly this kind of
  record for review.
- **Business-layer wiring.** The feature gets its own `vs-intent-to-model`
  ValueStream and `process-conversational-authoring` BusinessProcess, served
  by the existing `coa-executable-governance` course of action, realized by
  the `fn-conversational-authoring` ApplicationFunction — the same
  stream-per-outcome shape ADR-0033 set for the other four outcomes. See
  [Architecture Model: Skeleton](architecture-model-skeleton.md).

`plan.md` first cited this record as "ADR-0036"; that number went to the unrelated
element-id-prefix ADR during a rebase, so it filed as ADR-0037. A later item 8
(2026-11-01) amends the same still-Proposed record, because add-only was never a
deliberated decision and there was nothing to supersede. See "Candidate-delta
pipeline" below.

`archi-viewpoints.xml` is a **verbatim copy** of Archi's own viewpoint

own `ViewpointManager`/`Viewpoint` interpretation: an empty element or
relationship allow-set on a viewpoint means that half is unrestricted (every

value in `views.yaml` is Archi's own `id` attribute (`strategy`,
`value_stream`, `capability`, `application_cooperation`,

cross-layer view, never conformance-checked

## Running it

```bash
./scripts/run-modelling_specification.sh   # from the repo root
```

Runs `modelling_specification.app:app` with `uvicorn` from `platform/` on
`http://127.0.0.1:8001`
(`platform/packages/modelling-specification/README.md` §"Run the authoring

|---|---|---|

## Using it against another model (ADR-0045)

The package no longer assumes it sits beside this repo's model. Every path resolves
once from `model_io.py` at import, so another repo can install it and run
`build`, `render` and `validate` over its own YAML. Unset, a checkout uses its own
`architecture/model/` and an installed copy reads `architecture/model/` under the
current directory (`platform/packages/modelling-specification/README.md`).

| Variable | Sets | Default when `FRICTIONLESS_MODEL_DIR` is set |
|---|---|---|
| `FRICTIONLESS_MODEL_DIR` | Model YAML directory; `diagrams/` is written here | none |
| `FRICTIONLESS_THIRD_PARTY_DIR` | Vendored models directory | `third_party/` beside the model directory |
| `FRICTIONLESS_MODEL_NAME` | Model name and built file name | `frictionless-architect` |
| `FRICTIONLESS_C4_SYSTEM` | Element C4 diagrams are drawn around | none, so C4 diagrams are skipped |
| `FRICTIONLESS_ADR_DIR` | Where override ADR stubs are written | `docs/adr/` beside the model directory |

Each directory variable must name an existing directory, and the model name must be
a plain file name; otherwise the package refuses to start. `env_dir` also rejects a
blank or NUL-bearing value and canonicalises the path with `os.path.realpath`
(hardened 2026-11-06 against Snyk Code path-traversal findings; Snyk still reports
them, since it does not treat `env_dir` as a sanitiser)
(`platform/packages/modelling-specification/src/modelling_specification/model_io.py`).
A consumer installs the package as a Poetry git dependency and must also list
`llm-provider-config`, `digital-twin-knowledge-graph` and `pii-gateway` the same way,
because they are not on PyPI. The `puml` and `c4` modules only print; `render` places
their output, and anyone else redirects it
(`platform/packages/modelling-specification/README.md`).

## Candidate-delta pipeline

1. **Propose** (`platform/packages/modelling-specification/src/modelling_specification/authoring/delta.py`). An architect's natural-language
   request is sent to the configured LLM (ADR-0034, R4 — same
   `llm-provider-config`/`litellm` seam `controls-compliance-catalog`'s own
   LLM client uses, component id
   `modelling-specification.conversational-authoring`) with a system prompt
   grounded in the current model: elements as `id | type | name | description`,
   with descriptions cut to 300 characters so the LLM judges what an element is
   rather than guessing from its name (FR-019), plus contexts, views, relationships
   and convention rules. The prompt asks for strict JSON with seven required
   (possibly-empty) keys:
   `elements`, `relationships`, `views`, `view_membership_edits`,
   `element_edits`, `element_removals`, `relationship_removals`. The prompt
   matches named entities against the existing model by id rather than
   redeclaring them. **The original scope was add-only** (new elements,
   relationships and views only); **ADR-0037 item 8 lifted that restriction**
   (2026-11-01, after auditing the feature against a real authoring
   transcript that needed rename/remove workflows the carve-out didn't
   cover) — a request can now also rename an existing element
   (`element_edits`, name only: `desc`/`type` stay fixed because a folded
   multi-line `desc:` scalar makes the same precise, comment-preserving text
   surgery `model_io.py` already does for `view_membership_edits`'
   `members:` impractical to extend safely), remove an existing element
   (`element_removals`) or relationship (`relationship_removals`, matched
   by its `(type, source, target)` triple since relationships carry no
   stable id), or add/drop an existing element from an existing view's
   membership (`view_membership_edits`) — via text-surgical edits to
   `elements.yaml`/`relationships.yaml`/`views.yaml` that preserve
   hand-authored formatting rather than a full YAML rewrite. Nothing else
   about an existing element, relationship or view — its type, its
   description, a relationship's label, or anything about a view besides
   its membership — can be changed; such a request returns an empty delta
   rather than guessing. A reply too vague to form a concrete delta comes
   back as plain-text clarification instead of JSON: `router.py` returns it
   as `status: "message"`, with both the raw LLM text (`message`) and a
   pre-sanitised HTML rendering (`message_html`, via the new
   `markdown_render.py`) — `render_message_markdown` parses it with the
   `markdown` package then strips every tag/attribute outside a small
   allowlist (`p`, `br`, `strong`, `em`, `code`, `pre`, lists, `h1`-`h3`, `a`
   with `href`/`title` only, `http`/`https`/`mailto` schemes only) via `nh3`
   (the Ammonia sanitiser), so the untrusted LLM reply is inserted into the
   chat pane as HTML directly instead of the UI hand-rolling its own
   Markdown parser and allowlist-based sanitisation (GH #185)
   (`platform/packages/modelling-specification/src/modelling_specification/markdown_render.py`,
   `router.py`). A second proposal in
   the same conversation amends the still-pending delta rather than
   validating fresh against the last-applied state
   (`specs/EPIC-003-conversational-model-authoring/spec.md` Clarifications, 2026-10-08).
   Each call also carries the session's earlier turns (FR-018, ADR-0037 item 9):
   the last 20 messages, in process memory, recording only text the LLM was
   actually sent, so a flagged request stays out until resolved and then only its
   resolved form goes in. The prompt also includes the pending delta and tells the
   LLM to add to it rather than repeat it; anything it restates exactly is dropped.
   A past proposal found in neither the model nor the pending delta counts as
   discarded, so decisions need no entry of their own in the history
   (`specs/EPIC-003-conversational-model-authoring/data-model.md` §Conversation History).
   When the architect asks for a way forward instead ("what should I do
   about X") rather than describing one change, the LLM instead returns
   `{"options": [...]}` — 2-3 independently applicable candidate deltas,
   each with a `rationale` grounded in existing element ids and/or
   `conventions.yaml` rule ids. `router.py` validates every option through
   the same metamodel/duplicate/pattern pipeline below *before* the
   architect sees it, and `POST .../propose/select` turns the chosen one
   into the session's pending Candidate Delta. This is a deliberate
   deviation from the plan GH #68's filed sub-issues (#140-#151) describe —
   built directly against today's architecture rather than waiting for #142's
   future journey-API rework, for demo priority
   (`docs/adr/0041-structured-suggestion-options-in-delta-py.md`). See
   [Architecture Decision Log: ADR-0030 onward](decision-log-0030-onward.md). The
   split-screen UI's `renderProposeResponse` originally had no branch for
   `status: "options"`, so it printed the generic "Looks good -- no objections"
   text and silently dropped every option. Fixed (2026-11-05): `ui.py`'s
   `renderOptions` shows each option's rationale, convention references, proposed
   elements/relationships and validation caveats, with a "Pick this option" button
   that calls `propose/select`
   (`platform/packages/modelling-specification/src/modelling_specification/ui.py`).
   If the LLM call itself
   fails, `propose_delta` logs the provider detail server-side only and
   raises `DeltaProposalError` with a generic "The LLM call failed
   (<model>); see the server log for details." message, because the router
   returns that message in the 502 body and provider text must not leak to
   the client (CWE-209)
   (`platform/packages/modelling-specification/src/modelling_specification/authoring/delta.py`).
   Before any of that, the request is scrubbed by `pii-gateway` under its
   `conversational-authoring` context. A flagged match raises
   `PiiReviewRequired`, no LLM call is made, and `propose` returns
   `pii_review_required` with the matches until the architect resolves them
   through `POST .../propose/resolve-pii` (ADR-0014 amendment, GH #181;
   `specs/EPIC-003-conversational-model-authoring/contracts/api.md`).
   A resolved request gets the same grounding as any other; until 2026-11-05 it
   lost the contexts, views and relationships.
   A plain-text reply (`status: "message"`) can itself be Markdown, which the chat
   pane originally showed as literal text (GH #185). A client-side `renderMarkdown`
   fixed that on 2026-11-07 and was superseded the same day by the server-side
   `message_html` described above: `_message_response`
   (`platform/packages/modelling-specification/src/modelling_specification/router.py`)
   returns it, with `a` forced to `target="_blank"` and `rel="noopener noreferrer"`,
   and `ui.py` inserts it directly, never building HTML from the raw `message`. This
   avoids hand-rolling allowlist sanitisation for untrusted LLM output;
   `render_message_markdown` needs nothing beyond its input text, so another
   package's chat UI could reuse it, though none does yet
   (`platform/packages/modelling-specification/src/modelling_specification/markdown_render.py`).
   **Working indicator (GH #186, spec `003-llm-working-indicator`, Draft, 2026-11-08).**
   Before it, Send being disabled was the only sign an LLM call was in flight. Now
   `showThinking()` adds an italic, pulsing "Thinking…" chat message (`.msg.thinking`,
   animation off under `prefers-reduced-motion`) for the two paths that wait on the
   LLM: `sendRequest` (`propose`) and the PII-review button handler
   (`propose/resolve-pii`). Each removes it in a `finally`, so a reply, an error or a
   thrown exception all clear it, and `sendButton.disabled` is unchanged. It is
   classed `thinking`, never `agent`, so the `.msg.agent` selectors in the behave
   steps still mean "a real reply arrived". Choosing an option, applying or rejecting
   a delta and picking a view show none. It is client-only: no API, session or
   dependency change, and no new ADR or shared package, since a package needs a real
   second consumer (ADR-0034) and `controls-compliance-catalog` already has its own
   indicator. Streaming is out of scope. Tests are a `test_ui.py` markup check and two
   behave scenarios that set a new `FakeCompletion.delay` to observe the in-flight
   state; `tasks.md` marks T001-T011 done, T011 being a human check against a real LLM
   provider
   (`platform/packages/modelling-specification/src/modelling_specification/ui.py:88-90`,
   `platform/packages/modelling-specification/src/modelling_specification/ui.py:215-217`,
   `platform/packages/modelling-specification/src/modelling_specification/ui.py:701-714`,
   `platform/packages/modelling-specification/src/modelling_specification/ui.py:797-816`;
   `specs/EPIC-003-conversational-model-authoring/003-llm-working-indicator/spec.md`,
   `specs/EPIC-003-conversational-model-authoring/003-llm-working-indicator/plan.md`,
   `specs/EPIC-003-conversational-model-authoring/003-llm-working-indicator/research.md`,
   `specs/EPIC-003-conversational-model-authoring/003-llm-working-indicator/tasks.md`).
   The chat lists every kind of pending change and, until Apply, the render pane
   previews it in memory (FR-012a): new elements marked `+`, renamed ones `~`,
   removed ones gone, and a proposed or edited view opened as that view. A view
   that breaks its viewpoint still previews, but stays flagged and can't be applied.
   Before 2026-11-05 the UI and the preview endpoint only considered `elements` and
   `relationships`, so a delta that only proposed a view looked empty: nothing was
   drawn and Apply stayed disabled
   (`platform/packages/modelling-specification/src/modelling_specification/ui.py`).
2. **Validate** (`validation/metamodel.py`, `platform/packages/modelling-specification/src/modelling_specification/validation/conventions.py`,
   `validation/duplicates.py`, `validation/patterns.py`). The candidate is
   merged into the whole model (`model_io.merge_candidate`) and checked —
   never validated in isolation, so a change legal on its own but breaking
   referential integrity elsewhere is still caught:
   - **Metamodel**: pyArchimate's relationship-matrix legality and
     referential integrity; a delta that fails to even assemble (unknown
     type, dangling reference) surfaces as a `build_error` finding rather
     than raising. An `element_edits`/`element_removals`/
     `relationship_removals` entry is applied to the in-memory model the
     same way before assembly, so an unknown id, or a removal that would
     leave a dangling relationship end or an orphaned view node, is caught
     here — never silently cascaded (ADR-0037 item 8).
   - **Conventions**: `conventions.yaml`'s `naming`/`altitude`/
     `allowed-subset` rules (generic), `interposed-pattern` rules
     (pattern-specific, delegated to `patterns.py`), `required-neighbour`
     and `no-bypass` rules, and (added 2026-10-17) `no-restatement` — flags
     an element whose description shares a configurable-length (default 6)
     verbatim word run with a neighbour's description across a given
     relationship type/direction, so a Requirement can't be accepted if it
     merely restates the Outcome it realizes instead of adding something
     the Outcome didn't already say
     (`platform/packages/modelling-specification/src/modelling_specification/validation/conventions.py` `_check_no_restatement`,
     `_longest_shared_run`). A malformed rule raises
     `ConventionRuleError` naming the offending `id` — never silently
     skipped.
   - **Duplicates**: an element is flagged if at least two of
     {`name`, `type`, `desc`} match an existing element — `type` by exact
     equality, `name`/`desc` via `rapidfuzz.fuzz.token_sort_ratio >= 80`.
     Current/Transition/Target state is never a differentiator; a duplicate
     across states is still flagged, with state handled by the keep/merge/
     reject decision instead.
   - **Patterns**: a proposed *direct* relationship that matches a
     `conventions.yaml` `interposed-pattern` rule is flagged — not because a
     direct relationship is illegal, but because an established intermediary
     pattern exists for that shape. No rule matching is not itself grounds
     to flag. On `accept-pattern`, the agent synthesizes the intermediary
     element(s) and the two-leg relationship chain itself, rather than
     discarding the candidate and asking the architect to redescribe it.
3. **Fix on failure** (`platform/packages/modelling-specification/src/modelling_specification/validation/fixes.py`). Every rejection carries a
   deterministic `proposed_fix`, never a second LLM call: a metamodel
   violation's fix is the nearest legal relationship type for the same
   (source, target) type pair, read from pyArchimate's own matrix; a
   convention violation's fix is the value implied by the violated rule's
   own `params`.
4. **Decide and apply**. Session state (`platform/packages/modelling-specification/src/modelling_specification/authoring/state.py`) tracks each
   Candidate Delta through `proposed → validated/flagged → applied/
   discarded`, in-process memory only — no database, no resume path. An
   interrupted session's pending delta is simply dropped. Only `applied`
   writes to `architecture/model/`, through `model_io.py`'s write path:
   `append_delta` for new elements/relationships/views (additive-only), and
   (ADR-0037 item 8) a second, scoped set of text-surgical writers —
   `apply_view_membership_edits`, `apply_element_edits`,
   `apply_element_removals`, `apply_relationship_removals` — that locate
   and rewrite or delete only the exact line range of the entry being
   changed, so hand-authored comments and formatting elsewhere in
   `elements.yaml`/`relationships.yaml`/`views.yaml` survive untouched.
   Overriding a flagged objection (`platform/packages/modelling-specification/src/modelling_specification/authoring/overrides.py`) drafts the ADR
   stub described above; the rationale is optional and left blank if the
   architect gives none.
5. **Render**. On accept, the affected element(s)/view render live via
   `rendering.py` in the split-screen **Conversational Authoring UI**
   (`if-modelling-authoring-ui`, see [Portal](portal.md) and
   [Architecture Model: Ecosystem](architecture-model-ecosystem.md)). A view
   request that resolves to more than one plausible view, or none, asks the
   architect to disambiguate rather than guessing.

## Business and model wiring

`fn-conversational-authoring` is the ApplicationFunction serving this
feature; it reads `do-metamodel` and `do-convention-rules`, writes
`do-candidate-arch`, serves `fn-notation-engine` (live rendering), and is
exposed via `if-modelling-authoring-ui`. `sw-pyarchimate` and `sw-rapidfuzz` serve it (ADR-0044), and an overridden objection triggers `fn-override-escalation`, which writes the ADR stub to `do-adr`. It realizes
`process-conversational-authoring` at the business layer. It is scoped not
by a normal per-stage Artefact Flow view but by its own cross-layer "Feature
Steel Thread" view, `view-gh108-conversational-authoring` (a `layered`
viewpoint view, diagram `layered/fn-conversational-authoring`), which traces
the feature through every layer using only pre-existing edges. See
[Architecture Model: Artefact Flow](architecture-model-artefact-flow.md) and
[Architecture Model: Migration](architecture-model-migration.md) for the
full element-level treatment, and
[Architecture Model: Skeleton](architecture-model-skeleton.md) for
`vs-intent-to-model`, `process-conversational-authoring`,
`req-conversational-authoring-alignment` and
`cap-conversational-governance`.
