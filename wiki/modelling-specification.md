Subsystem 6 of the platform, `platform/packages/modelling-specification`: a
conversational agent (GH #108) that turns a natural-language request from an
architect into a validated ArchiMate model delta, live-rendered on accept.
The package also now holds the deterministic model build/render/validate
logic that root's scripts and the `model-archimate` skill used to carry
themselves. See [Architecture Model](architecture-model.md) for the model
elements this feature adds, and [Decision Log](decision-log.md) for
ADR-0037, the record of its five load-bearing design decisions.

## Why the code lives here

[ADR-0037](decision-log.md) (Proposed 2026-10-10) decided the package's
shape and three related questions `plan.md`'s Constitution Check flagged as
load-bearing:

- **Package location.** A new `platform/packages/modelling-specification`
  sibling package, matching the `controls-compliance-catalog` pattern
  (ADR-0002, ADR-0011) — not `src/frictionless_architect/`, which is the
  pre-migration flat layout.
- **One implementation, three callers.** `architecture/model/build.py`'s
  YAML load/merge/validate logic and `render_diagrams.py`'s view-render logic
  moved into this package as `model_io.py` (934 lines) and `rendering.py`
  (407 lines). Root's `build.py`, `render_diagrams.py` and the
  `model-archimate` skill's `validate.py` are now thin wrappers that shell
  into the platform venv's CLI — `poetry run --directory platform python -m
  modelling_specification.cli build|render|validate`
  (`platform/packages/modelling-specification/src/modelling_specification/cli.py`). This keeps ADR-0001's
  root-never-imports-a-platform-package boundary: root only shells out, as
  it always did, just uniformly across all three entry points now instead of
  carrying its own copy of the logic.
- **Enterprise Convention Rules move to data.** A new
  `architecture/model/conventions.yaml` holds organisation-specific
  authoring rules (naming/altitude conventions, interposed-element shapes)
  as inspectable, editable YAML, aggregated under `store-frameworks`
  alongside `do-metamodel`. The fixed ArchiMate 3.2 metamodel rules
  themselves stay sourced from pyArchimate — only the enterprise/domain
  layer on top is externally configurable
  (`platform/packages/modelling-specification/src/modelling_specification/validation/conventions.py`).
- **Overrides become ADR stubs, not ledger entries.** When an architect
  overrides a flagged objection, the override is recorded as an
  auto-drafted `Status: Proposed` ADR stub under `docs/adr/`
  (`platform/packages/modelling-specification/src/modelling_specification/authoring/overrides.py`), not appended to `store-ledger` — an override
  is an architecture-governance decision, not controls/compliance evidence,
  and the existing `adr-auditor` sweep already picks up exactly this kind of
  record for review.
- **Business-layer wiring.** The feature gets its own `vs-intent-to-model`
  ValueStream and `process-conversational-authoring` BusinessProcess, served
  by the existing `coa-executable-governance` course of action, realized by
  the `fn-conversational-authoring` ApplicationFunction — the same
  stream-per-outcome shape ADR-0033 set for the other four outcomes. See
  [Architecture Model: Skeleton](architecture-model-skeleton.md).

`plan.md` originally cited this record as "ADR-0036"; that number was taken
by the unrelated element-id-prefix-scheme ADR during a rebase, so it filed
as ADR-0037 instead, with both `plan.md` references corrected to match.

## Running it

```bash
./scripts/run-modelling_specification.sh   # from the repo root
```

Runs `modelling_specification.app:app` with `uvicorn` from `platform/` on
`http://127.0.0.1:8001`
(`platform/packages/modelling-specification/README.md` §"Run the authoring

needs an LLM provider configured for the
`modelling-specification.conversational-authoring` component (see

## Candidate-delta pipeline

1. **Propose** (`platform/packages/modelling-specification/src/modelling_specification/authoring/delta.py`). An architect's natural-language
   request is sent to the configured LLM (ADR-0034, R4 — same
   `llm-provider-config`/`litellm` seam `controls-compliance-catalog`'s own
   LLM client uses, component id
   `modelling-specification.conversational-authoring`) with a system prompt
   that asks for strict JSON: `{"elements": [...], "relationships": [...]}`.
   The prompt matches named entities against the existing model by id and
   refuses to re-declare anything that already exists — the agent can only
   **add**, never rename/edit/remove via this path. A reply too vague to
   form a concrete delta comes back as plain-text clarification instead of
   JSON. A second proposal in the same conversation amends the still-pending
   delta rather than validating fresh against the last-applied state
   (`specs/004-conversational-model-authoring/spec.md` Clarifications, 2026-10-08).
2. **Validate** (`validation/metamodel.py`, `platform/packages/modelling-specification/src/modelling_specification/validation/conventions.py`,
   `validation/duplicates.py`, `validation/patterns.py`). The candidate is
   merged into the whole model (`model_io.merge_candidate`) and checked —
   never validated in isolation, so a change legal on its own but breaking
   referential integrity elsewhere is still caught:
   - **Metamodel**: pyArchimate's relationship-matrix legality and
     referential integrity; a delta that fails to even assemble (unknown
     type, dangling reference) surfaces as a `build_error` finding rather
     than raising.
   - **Conventions**: `conventions.yaml`'s `naming`/`altitude`/
     `allowed-subset` rules (generic), `interposed-pattern` rules
     (pattern-specific, delegated to `patterns.py`), `required-neighbour`
     and `no-bypass` rules, and (added 2026-10-17) `no-restatement` — flags
     an element whose description shares a configurable-length (default 6)
     verbatim word run with a neighbour's description across a given
     relationship type/direction, so a Requirement can't be accepted if it
     merely restates the Outcome it realizes instead of adding something
     the Outcome didn't already say
     (`platform/packages/modelling-specification/src/modelling_specification/validation/conventions.py` `_check_no_restatement`,
     `_longest_shared_run`). A malformed rule raises
     `ConventionRuleError` naming the offending `id` — never silently
     skipped.
   - **Duplicates**: an element is flagged if at least two of
     {`name`, `type`, `desc`} match an existing element — `type` by exact
     equality, `name`/`desc` via `rapidfuzz.fuzz.token_sort_ratio >= 80`.
     Current/Transition/Target state is never a differentiator; a duplicate
     across states is still flagged, with state handled by the keep/merge/
     reject decision instead.
   - **Patterns**: a proposed *direct* relationship that matches a
     `conventions.yaml` `interposed-pattern` rule is flagged — not because a
     direct relationship is illegal, but because an established intermediary
     pattern exists for that shape. No rule matching is not itself grounds
     to flag. On `accept-pattern`, the agent synthesizes the intermediary
     element(s) and the two-leg relationship chain itself, rather than
     discarding the candidate and asking the architect to redescribe it.
3. **Fix on failure** (`platform/packages/modelling-specification/src/modelling_specification/validation/fixes.py`). Every rejection carries a
   deterministic `proposed_fix`, never a second LLM call: a metamodel
   violation's fix is the nearest legal relationship type for the same
   (source, target) type pair, read from pyArchimate's own matrix; a
   convention violation's fix is the value implied by the violated rule's
   own `params`.
4. **Decide and apply**. Session state (`platform/packages/modelling-specification/src/modelling_specification/authoring/state.py`) tracks each
   Candidate Delta through `proposed → validated/flagged → applied/
   discarded`, in-process memory only — no database, no resume path. An
   interrupted session's pending delta is simply dropped. Only `applied`
   writes to `architecture/model/`, through `model_io.py`'s write path.
   Overriding a flagged objection (`platform/packages/modelling-specification/src/modelling_specification/authoring/overrides.py`) drafts the ADR
   stub described above; the rationale is optional and left blank if the
   architect gives none.
5. **Render**. On accept, the affected element(s)/view render live via
   `rendering.py` in the split-screen **Conversational Authoring UI**
   (`if-modelling-authoring-ui`, see [Portal](portal.md) and
   [Architecture Model: Ecosystem](architecture-model-ecosystem.md)). A view
   request that resolves to more than one plausible view, or none, asks the
   architect to disambiguate rather than guessing.

## Business and model wiring

`fn-conversational-authoring` is the ApplicationFunction serving this
feature; it reads `do-metamodel` and `do-convention-rules`, writes
`do-candidate-arch`, serves `fn-notation-engine` (live rendering), and is
exposed via `if-modelling-authoring-ui`. It realizes
`process-conversational-authoring` at the business layer. It is scoped not
by a normal per-stage Artefact Flow view but by its own cross-layer "Feature
Steel Thread" view, `view-gh108-conversational-authoring` (a `layered`
viewpoint view, diagram `layered/fn-conversational-authoring`), which traces
the feature through every layer using only pre-existing edges. See
[Architecture Model: Artefact Flow](architecture-model-artefact-flow.md) and
[Architecture Model: Migration](architecture-model-migration.md) for the
full element-level treatment, and
[Architecture Model: Skeleton](architecture-model-skeleton.md) for
`vs-intent-to-model`, `process-conversational-authoring`,
`req-conversational-authoring-alignment` and
`cap-conversational-governance`.
