## The feature: AI-assisted policy/standard conversion to OSCAL

### Problem and user stories

The feature builds the first real path from a verbatim policy or regulatory
standard document to machine-readable OSCAL
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/spec.md`),
in three prioritised user stories:

- **US1 (P1)** — convert a verbatim document (PDF, Word, spreadsheet/CSV,
  Markdown, or text) into Trestle-editable Markdown.
- **US2 (P2)** — assemble that Markdown into an OSCAL Catalog + Profile.
- **US3 (P3)** — resolve a Profile against its Catalog(s) into a fully
  resolved OSCAL Catalog.

Edge cases called out in the spec: control-identifier collisions across
documents, LLM errors/timeouts, resubmission overwriting a prior conversion
under the same identifier, and documents large enough to need chunking
across LLM calls.

### Pipeline and architecture

The pipeline runs behind its own FastAPI app —
`uvicorn controls_compliance_catalog.app:app`
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/quickstart.md`)
— not a router mounted on the flat visualiser app. This reverses an interim
2026-09-24 decision (see ADR-0005's "Implementation status" notes): once
this package got its own app, the shared `frictionless_architect/app.py`
reverted to being "the visualiser's alone again" until the visualiser
itself is extracted into `schema-visualizer-api`.

The end-to-end flow
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/plan.md`
Summary): normalize → chunked AI-assisted conversion to Trestle-editable
Markdown → Trestle structural validation → a Compliance-Officer approval
gate → Trestle import/assemble into an OSCAL Catalog + Profile → Trestle
profile-resolve into a fully resolved Catalog.

Because neither an LLM client nor a forensic audit ledger existed in code
before this feature (both were architecture-model vision only — `ext-llm`,
`store-ledger`), the plan stands up minimal, narrowly-scoped first-party
versions of each rather than a general-purpose framework
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/research.md`
R2/R3):

- `platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/llm_client.py` — a thin wrapper over `litellm`, one call shape
  (`convert_chunk`), errors normalized to a single `LlmConversionError`.
- `ledger.py` — an append-only JSONL forensic ledger at a path shaped like
  `<data_dir>/forensic-ledger.jsonl`, one line per event, no
  update/delete API — deliberately not a database, since there's no new
  infra need at this scale (single-user MVP, ADR-0024) and a future
  feature can migrate it without changing this feature's `LedgerEntry`
  contract.

Document normalization (R4) uses small, format-specific libraries rather
than one heavyweight document-conversion dependency: `pypdf` (PDF),
`python-docx` (Word), stdlib `csv` + `openpyxl` (spreadsheet/CSV), and
direct UTF-8 reads for Markdown/text. All formats converge on a common
sectioned representation (`SourceMapEntry`) that also defines chunk
boundaries for documents too large for one LLM context window (FR-018,
R5) — chunking reuses section boundaries rather than a fixed-token sliding
window, so a control's full statement never splits across a chunk edge.

Trestle itself is driven via its Python API in-process
(`trestle.core.commands.*`), not by shelling out to the `trestle` CLI
(R6) — avoiding subprocess/PATH/venv fragility in tests and CI, since
`compliance-trestle` is already a library dependency.

### Relationship to `oscal-document-workbench`

`oscal-document-workbench` (Apache-2.0, `oscal-compass-lab/compliance-trestle-skills`)
solves an adjacent but different problem — drafting an OSCAL SSP against an
*already-existing* Catalog/Profile — and is agent-only shell tooling, not an
importable library a synchronous FastAPI handler can call. The plan
explicitly does not vendor or depend on it
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/research.md`
R10); instead it **ports** two of its designs as native Python, each carrying
an Apache-2.0 attribution header per §4 of that license:

- its sectioning/traceability design, `extract-legacy-doc.sh` in the upstream
  `oscal-document-workbench` repo (not itself a source of this page) → this
  feature's `SourceMapEntry`/normalizer design (R4).
- its validation-report shape, `validate-oscal-package.sh` in that same
  upstream repo → this feature's `ValidationReport` (R6).

This port decision is recorded as an update to ADR-0030, parallel to that
ADR's existing OSCAL-vendoring rationale.

### Data model

Key entities
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/data-model.md`),
all first-party Pydantic v2 models unless noted as a filesystem artefact:

- **SourceDocumentIdentifier** — the stable partition key threaded through
  every other entity; also the Trestle workspace slug (R7).
- **NormalizedDocument** / **SourceMapEntry** — normalization output and its
  per-section status (`pending` / `converted` / `unconvertible`).
- **TrestleEditableMarkdownCatalog** — filesystem artefact + status record;
  lifecycle `converting → converted → validating → validated` or
  `conversion_failed` / `validation_failed` (mirrored in the architecture
  model as `do-oscal-catalog`'s `status-lifecycle` property).
- **ValidationReport** — ported shape, always carries the note "Structural
  validation only; not an audit opinion." (FR-010/SC-004).
- **ApprovalRecord** — derived from the ledger, not an independent store
  (R9): `regulatory-standard` documents always re-require approval;
  `custom-policy` documents stay approved across later re-conversions of
  the same identifier.
- **OscalCatalog** / **OscalProfile** / **ResolvedOscalCatalog** — distinct
  filesystem artefacts, never merged into one blob (FR-009).
- **GoldenDataset** — test-only fixtures, read-only, never written back
  into `third_party/`.
- **LedgerEntry** — the ledger's own append-only record shape
  (`entry_id`, `actor`, `action`, `outcome`, `detail`, ...).

State machines for the catalog/source-map/approval lifecycles, a class
diagram, and a pipeline activity diagram are all rendered under this
feature's own `diagrams/` directory
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/data-model.md`).

### API surface

All endpoints are mounted under `/oscal` on the package's own FastAPI app
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/contracts/api.md`),
following `TECHNICAL.md`'s action-based-endpoint conventions:

- `POST /oscal/conversions` — submit a document (US1); `201` with the
  source map, validation report, and workspace path, or a `conversion_failed`
  / `validation_failed` status on failure. `409` is reserved for a
  conversion already in flight under the same identifier — resubmission
  itself is not an error (FR-015 overwrites).
- `GET /oscal/conversions/{source_document_id}` — poll the latest result.
- `POST /oscal/conversions/{source_document_id}/approve` — the Compliance
  Officer/Auditor approval gate (FR-011).
- `POST /oscal/assemblies` — Trestle import + author/assemble into a
  Catalog + Profile (US2); `403` if the approval gate isn't satisfied,
  `502` carries a specific Trestle failure rather than a partial artefact.
- `POST /oscal/resolutions` — Trestle profile-resolve into a fully
  resolved Catalog (US3); `422` if the Catalog/Profile pair doesn't exist
  yet.

No endpoint exposes the forensic ledger directly, and no endpoint runs the
golden-dataset validation — that stays a test-only path.

### Golden-dataset validation

FR-006/FR-007 require the pipeline's accuracy to be proven against two
vendored golden datasets — NIST SP 800-53 rev5 (`third_party/oscal-content`)
as conversion input, and FedRAMP's pre-resolved baselines
(`third_party/fedramp-automation`) as expected resolution output — never as
production input (FR-008). This runs as a separate `pytest -m golden` job,
excluded from the default fast suite because it invokes a real LLM and real
Trestle
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/research.md`
R8). "Correctly identified, faithfully worded"
(SC-002/SC-003) is judged by LLM-as-judge paraphrase comparison, not exact
string match — this is also modelled in the architecture graph as
`techproc-oscal-golden-check` (see [Architecture Views & Diagrams](architecture-diagrams.md)
for the rendered Technology-layer diagram).

### Control conversion playground (GH #76)

Alongside the `/oscal` pipeline the package serves an interim developer tool at
`/playground` (`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/api.py`): a single-control
page that runs two conversions to Trestle Markdown and compares them, so the AI step
can be eyeballed against Trestle's own output one control at a time. It is explicitly
not a journey-API role, and it is a precondition for the bulk golden-dataset testing
in #49 (the issue wording lives in GH #76, not in these sources).

**Two lanes, one screen.** The page shows both lanes' stages side by side
(`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/api.py`, `.stages`):

- *Reference* — pasted OSCAL → Trestle's own conversion → reference Markdown.
  `convert_oscal_control_to_markdown` parses the input with `yaml.safe_load`
  (JSON also works, as it is valid YAML), wraps a bare control into a throwaway
  `Catalog`, and drives `CatalogAPI.write_catalog_as_markdown` in a temp directory
  — the same code path as `trestle author catalog-generate`, never a hand-rolled
  template (`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/convert.py`). The reference lane runs automatically on page
  load and, debounced, on every edit of the OSCAL box (`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/api.py`).
- *Candidate* — control prose → AI conversion → candidate Markdown.
  `convert_control_prose_to_markdown_candidate` loads the system prompt and calls
  `llm_client.convert_chunk`; the AI step only ever produces Markdown from prose
  and never touches OSCAL (`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/convert.py`).

**Endpoints.** `POST /playground/oscal-to-markdown` (body `{oscal}`) and
`POST /playground/prose-to-markdown-candidate` (body `{prose}`) each return
`{markdown}` or a `422` carrying `{error_code, message}` — `invalid_oscal` or
`invalid_prose` (`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/api.py`). Because the lanes are separate calls, one
lane's failure shows in the UI without blanking the other's output; the behave
scenarios cover empty prose and malformed YAML (`platform/packages/controls-compliance-catalog/tests/features/playground_oscal_to_markdown.feature`, `platform/packages/controls-compliance-catalog/tests/features/playground_prose_to_markdown_candidate.feature`).

**Comparison view.** The two Markdown panes get a line-level LCS diff; within a
changed line pair, a word-level diff highlights only the differing words, but only
when at least 40% of the words are shared (`SIMILAR_ENOUGH`), to avoid noisy
diffs of unrelated lines (`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/api.py`). A toggle switches between highlighted
and plain output, a "Sync scrolling" checkbox keeps the panes at the same scroll
fraction, and each text area and pane has a copy button.

**The conversion prompt** lives in `platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/prompts.yaml` under
`prose_to_trestle_markdown.system`, not in Python. `load_system_prompt` re-reads it on
every conversion, so edits apply on the next click with no restart
(`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/prompts.py`). The current prompt spells out Trestle's heading form
(`# <id> - \[\] <Title>`), the "Control Statement" section, verbatim prose, and carries
a worked example (`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/prompts.yaml`). Generating the few-shot examples from
Trestle's real output, and exposing the prompt in the UI, are deferred follow-ups, not
built.

**The AI call.** `llm_client.convert_chunk(prompt, system)` resolves provider, model
and credentials through `llm_provider_config.resolve_call` for the component id
`controls-compliance-catalog.candidate-conversion`, so a per-component override wins
over the global default; it rejects empty prose, wraps configuration, credential and
provider failures in `LlmConversionError`, and strips a single surrounding code fence
that models often add (`platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/llm_client.py`). `app.py` also mounts the shared settings
router at `/settings/llm`, declaring this one component
("Control conversion (AI candidate)"), and the playground header links to it
(`app.py`, `platform/packages/controls-compliance-catalog/src/controls_compliance_catalog/playground/api.py`). See [LLM Provider Configuration](llm-provider-config.md).

**Running it.** `scripts/run-playground.sh` starts the app on `http://127.0.0.1:8001`
with reload (`scripts/run-playground.sh`). Its header comment still says the playground
takes "control/catalog JSON"; the code now takes YAML (and JSON).

### Constitution and security posture

The plan's Constitution Check
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/plan.md`)
passes with one explicit, spec-directed exception under Principle V (Security): FR-016 sends verbatim
document content to the LLM with no redaction step, a deliberate deviation
from ADR-0014's PII-gateway rule, scoped narrowly — policy/standard
documents are organizational artefacts inside the trust boundary, not
collaboration-tool chatter carrying PII/PHI. This is recorded as ADR-0031.
Principle II (Testing Standards) is satisfied by using **real** Trestle
invocations in tests rather than mocks (FR-012) — mocking the one
integration surface under test would hide the behaviour the tests exist to
catch.

The package depends on no other platform package
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/plan.md`
Structure Decision): the forensic ledger conceptually belongs to subsystem 3
(`digital-twin-knowledge-graph`), so `ledger.py` stays a narrow,
package-local ledger until that package exists to take it over.

### Running it

From `platform/`: `poetry install`, then `poetry run uvicorn
controls_compliance_catalog.app:app --reload` serves `/oscal/*`
(`platform/packages/controls-compliance-catalog/specs/001-oscal-ai-conversion/quickstart.md`).
The golden-dataset submodules
(`third_party/oscal-content`, `third_party/fedramp-automation`) must be
checked out first. For the playground, run `scripts/run-playground.sh` and open `/playground`. `scripts/platform_checks.sh` gates the package (lock
check, pyright, per-package mypy, pytest at 90% coverage) and is folded
into `scripts/pre_commit_checks.sh` — see [Development & Quickstart](development.md).
