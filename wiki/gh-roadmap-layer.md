## What it is

Spec 003 (GH #95, decision ADR-0035) maps GitHub milestones, releases and issues
into the architecture model as ArchiMate **Implementation & Migration** elements.
It is milestone-first and user-facing, "not a dump of every issue"
(`specs/003-gh-roadmap-archimate/spec.md` §Input). A script,
`architecture/model/import_gh_roadmap.py`, reads GitHub through the `gh` CLI and
writes a generated, committed YAML layer in `architecture/model/gh-roadmap/`;
`build.py` merges it like any other layer
(`specs/003-gh-roadmap-archimate/plan.md` §Summary). See
[Architecture Model](architecture-model.md) for the model itself and the
[Architecture Decision Log](decision-log.md) for ADR-0035.

## Mapping

(`specs/003-gh-roadmap-archimate/spec.md` §Mapping)

| GitHub | Becomes | Relationships |
|---|---|---|
| Milestone | Plateau | Realizes a business function (`bfn-*`) it names |
| Issue with its own milestone | Work Package | Realizes one Deliverable; aggregates sub-issues; triggers issues it blocks |
| Published release (not draft/pre-release) | Deliverable | Realizes the Plateau it names |
| Milestone with ≥1 Work Package | Unreleased Deliverable | Realizes the milestone's Plateau |
| Cross-milestone issue dependency | none | One Plateau → Plateau Triggering |

Scope rules:

- An issue is in scope only if it carries **its own** milestone; nothing is inferred
  from a parent, descendant or label (FR-002, `spec.md`; R5, `specs/003-gh-roadmap-archimate/research.md`).
- Drafts and pre-releases are skipped (`specs/003-gh-roadmap-archimate/data-model.md` §Scope).
- A Work Package realizes exactly one Deliverable and never a Plateau directly
  (FR-003). Open ones realize the milestone's unreleased Deliverable; a closed one
  realizes the first release, among those naming its Plateau, published after its
  `closedAt`, else the unreleased one (`specs/003-gh-roadmap-archimate/data-model.md` §"Which Deliverable a Work
  Package realizes"). GitHub has no issue-to-release link, so close time against
  publish time is the only signal (R6, `specs/003-gh-roadmap-archimate/research.md`).
- Releases attach to a Plateau only by naming its model id in the notes.

## Ids

Ids are prefixed by element type, never by source system; `gh-*` appears only as a
prop key (`specs/003-gh-roadmap-archimate/data-model.md` §"Element ids").

| Element | Id |
|---|---|
| Plateau | `plat-<title-slug>-<n>` |
| Release Deliverable | `del-release-<tag-slug>` |
| Unreleased Deliverable | `del-<title-slug>-<n>-unreleased` |
| Work Package | `wp-<title-slug>-gh-<n>` (title slug cut at a word boundary to ≤40 characters) |

Retitling a milestone or issue changes its id, so hand-authored references fail the
build until updated; this is deliberate (R4). Slug helpers are in
`architecture/model/import_gh_roadmap.py:88-120`.

## Ownership split

The importer owns Plateaus for milestones, both kinds of Deliverable, Work Packages
and their links. Hand-authored: the baseline Plateau `plat-baseline`, Gaps, Strategy
elements (Capability, Course of Action) and links to technology
(`specs/003-gh-roadmap-archimate/data-model.md` §"Ownership split"). A Gap is an architectural judgement GitHub
cannot express (R1), so Gaps are `gap-<spec-slug>` per ADR-0035, related to
Plateaus by Association only. A scan that proposes Gaps from specs with a mapping
file is planned separately (GH #102) and is not built.

Hand-authored files may reference importer ids; if GitHub deletes the object the
build fails with an unknown id. Per FR-011 the same change retired
`plat-runtime-mvp` and `plat-runtime-target` in favour of the generated Plateaus.

## Relationships

(`specs/003-gh-roadmap-archimate/data-model.md` §"Emitted relationships")

- Work Package → Deliverable and Deliverable → Plateau: Realization.
- Parent/child (both imported): Aggregation parent → child.
- "Blocked by" between Work Packages: Triggering blocker → blocked. Across
  milestones: one de-duplicated Plateau → Plateau Triggering, no self-loops.
- Plateau → business function: Realization, only when the milestone description
  names an existing `bfn-*` id.
- No Work Package → Plateau link at all (R2).
- A link implied by a chain of emitted links is dropped; the check looks only at the
  importer's own links, so output stays a function of GitHub state
  (`architecture/model/import_gh_roadmap.py:294-316`).
- Links with an out-of-scope end are dropped.

## Untrusted text

GitHub text is untrusted. `bfn-*` / `plat-*` tokens are honoured only on an exact
match against an existing element of the right type; no fuzzy matching (R10). Text
enters YAML only via `yaml.safe_dump` (FR-006; `specs/003-gh-roadmap-archimate/data-model.md` §"Untrusted text and
id tokens"). Token patterns: `architecture/model/import_gh_roadmap.py:217-218`.

## Running it

(`specs/003-gh-roadmap-archimate/contracts/importer-cli.md`)

```bash
poetry run python architecture/model/import_gh_roadmap.py [--repo OWNER/NAME] [--check]
poetry run python architecture/model/build.py
```

| Exit | Meaning |
|---|---|
| 0 | Layer written or already current (with `--check`: current) |
| 1 | `--check` only: layer is stale |
| 2 | `gh` missing, unauthenticated, rate-limited, errored or unparseable output; nothing written |

Behaviour:

- Milestones and releases come from paginated REST; issues (with `closedAt`, parent,
  `blockedBy`) from one paginated GraphQL query. The cap is 1000 issues (ten pages
  of 100); if `hasNextPage` is still true the run fails rather than import a partial
  set (R8; `architecture/model/import_gh_roadmap.py:35-36`).
- All three files are rendered in memory and then replaced atomically
  (temp files, then `os.replace`); a failed fetch leaves the layer untouched (R9, FR-009).
- Output is sorted with no timestamps, so unchanged GitHub state gives byte-identical
  files (FR-007, SC-002).
- `build.py` treats `gh-roadmap/` as an optional layer through `MODEL_LAYERS`; a
  missing directory is skipped (R3; `contracts/importer-cli.md` §"Contract with
  `build.py`"). The importer is injected with a `run_gh` runner so unit tests use
  recorded JSON (R13).
- One view per milestone (`implementation_migration` viewpoint, diagram
  `migration/<plateau id>`) plus the overview; diagrams come from
  `render_diagrams.py` (R11, FR-010).

## Issue lifecycle

State is derived on each run, not stored (`specs/003-gh-roadmap-archimate/data-model.md` §"Issue lifecycle"):
open ⇄ closed changes `gh-state` and possibly the Deliverable realized; a release
published after a close moves the Work Package to that release; a milestone change
retargets Realization; removing the milestone or deleting the issue removes the
element (the model is a current-state ledger, not history).

## Performance

SC-007 / R14 (GH #104) budget a full import at the 1000-issue cap to 2 minutes
wall-clock. Measured: this repo's actual run (~100 issues, one GraphQL page)
takes 4–6s over 4 `gh` calls (repo resolve, milestones, releases, one issues
page), each 0.5–2s; a synthetic 1000-issue fixture with network mocked out
built and rendered the layer in under 2s of pure computation. The bottleneck
at the cap is ten sequential `gh api graphql` round trips, not compute, so the
measurements support keeping the cap rather than raising it
(`specs/003-gh-roadmap-archimate/spec.md` §SC-007; `research.md` R14).

## Invariants

The spec lists ten tested invariants (`specs/003-gh-roadmap-archimate/data-model.md` §Invariants): unique
type-prefixed ids; resolvable endpoints; no element from an issue without its own
milestone; byte-identical output; every link legal under the ArchiMate 3.2 matrix;
no Work Package realizes a Plateau; drafts and pre-releases never yield a
Deliverable; unmatched tokens create no relationship; an unreleased Deliverable
exists only when a Work Package realizes it.
