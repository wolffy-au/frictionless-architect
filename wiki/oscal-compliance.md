This topic covers the vendored OSCAL/FedRAMP reference content, the
`compliance-trestle` dependency, and how the two together back the platform's
compliance-automation vision. The decision behind all of it is
[ADR-0030](docs/adr/0030-vendor-oscal-reference-content.md) — see
[Architecture Overview](architecture.md) for where it sits in the wider
decision log.

## Why this exists

The architecture model already commits to OSCAL-based compliance in its
vision — `process-policy-authoring`/`fn-policy-authoring` and
`process-oscal-conversion`/`fn-oscal-conversion` name "Trestle Markdown" and a
"Trestle round-trip," and a full artefact chain of `bo-oscal-*`/`art-oscal-*`
DataObjects models Catalog, Profile, Component Definition, SSP, and
Assessment Results — but until ADR-0030 none of it was backed by real
content or tooling: `sample-data/oscal/` held only two illustrative PlantUML
diagrams, `third_party/` had only the `it4it` submodule, and
`ARCHITECTURE.md` listed "which OSCAL tool?" as an open question
(`docs/adr/0030-vendor-oscal-reference-content.md` §Context). See
[Architecture Model: Artefact Flow](architecture-model-artefact-flow.md) for the artefact-flow elements
this content now grounds.

## Split vendoring approach

[ADR-0029](architecture.md)'s IT4IT pattern — a `third_party/` submodule of
ArchiMate-schema YAML, merged into the model by `build.py`'s shared
`det_id()`/`NS` pass — doesn't transfer to OSCAL: NIST/FedRAMP content is
real OSCAL JSON/XML in OSCAL's own schema, and `compliance-trestle` is a
Python library/CLI, not a reference model. ADR-0030 splits the approach by
what each upstream actually is (`third_party/README.md`):

| Submodule | Upstream | License | Role |
|---|---|---|---|
| `third_party/oscal` | [`usnistgov/OSCAL`](https://github.com/usnistgov/OSCAL) | Public domain / CC0 | OSCAL's own schemas/models — ground truth for the schema-alignment review, GH #24 |
| `third_party/oscal-content` | [`usnistgov/oscal-content`](https://github.com/usnistgov/oscal-content) | Public domain / CC0 | The real NIST SP 800-53 rev5 catalog and LOW/MODERATE/HIGH/PRIVACY baseline profiles as OSCAL JSON |
| `third_party/fedramp-automation` | [`GoComply/fedramp`](https://github.com/GoComply/fedramp) | CC0 core; vendors non-CC0-licensed Go deps | FedRAMP baseline catalogs (`bundled/catalogs/`) layered on the NIST catalog — no PRIVACY baseline |

All three are plain git submodules (`.gitmodules`) with **no `fork-sync`
entry** — read-only reference/example content the repo doesn't patch, not a
tracked fork — and none are consumed by `build.py`: there is nothing for
`det_id()` to hash or merge, since OSCAL catalogs/profiles aren't ArchiMate
model YAML (`docs/adr/0030-vendor-oscal-reference-content.md` §Decision,
§Consequences). This page takes only each submodule's top-level `README.md`
and `LICENSE.md` as sources, not the catalogs and profiles inside, so it
describes what each upstream is rather than the controls it contains.

### What each upstream says about itself

- **`oscal`** — NIST's main OSCAL project: the source of the OSCAL models, a
  set of hierarchical XML, JSON and YAML formats for publishing, implementing
  and assessing security controls. Its README lists sibling repositories,
  including OSCAL-Reference (model documentation) and OSCAL-Content, which is
  vendored here as `oscal-content` (`third_party/oscal/README.md`
  §"Project Repositories").
- **`oscal-content`** — example OSCAL content in XML, JSON and YAML against
  the latest stable OSCAL release. It has `examples/` organised by model, and
  `nist.gov/SP800-53/rev4` and `rev5` directories holding the SP 800-53
  catalog and its LOW/MODERATE/HIGH baselines. The format variants are
  generated by CI from `src/`, so the generated files are not meant to be
  edited (`third_party/oscal-content/README.md`).
- **`fedramp-automation`** (`GoComply/fedramp`) — a Go CLI,
  `gocomply_fedramp`, that turns OpenControl repositories into
  FedRAMP/OSCAL-format SSPs and converts an OSCAL SSP to a FedRAMP DOCX
  document; the README calls the DOCX output "work in progress"
  (`third_party/fedramp-automation/README.md` §Features, §"Exemplary usage").
  Its README doesn't mention the `bundled/catalogs/` baselines this repo
  vendors it for — that role comes from `third_party/README.md`.

`compliance-trestle` is the opposite case: an ordinary Poetry **main
dependency** (`pyproject.toml` — `"compliance-trestle (>=5.1.0,<6.0.0)"`,
alongside `fastapi`, `neo4j`, `uvicorn`), not a `third_party/` submodule. Per
[ADR-0002](architecture.md), `third_party/` is reserved for forks the repo
tracks and potentially patches; only trestle's published library/CLI
behaviour (Markdown-authoring, OSCAL round-trip) is needed, so it follows the
normal `poetry update`/Dependabot upgrade path instead of `fork-sync`
(`docs/adr/0030-vendor-oscal-reference-content.md` §Decision).

In the architecture model, trestle is `ext-trestle` — an `ApplicationComponent`
in the existing "External systems" convention alongside `ext-llm`, with a `Serving`/`Realization` edge into
`fn-oscal-conversion` (not `Flow`/`Access` like the peer-system externals) and
a `desc` noting it's "a third-party Python library/CLI dependency, not
vendored source" so it isn't mistaken for the `it4it-` vendored-content
pattern. See [Architecture Model: Ecosystem](architecture-model-ecosystem.md) for the full element
and its relationships. (ADR-0030 still names `ext-regsources` as a peer
external. The architecture model has since removed that element in the
Controls & OSCAL remodel, so the ADR text is out of date on this point.)

## Ported logic: `oscal-document-workbench`

A 2026-09-24 revision of ADR-0030 adds a third category besides "vendor as a
submodule" and "consume as a dependency".
`oscal-compass-lab/compliance-trestle-skills` (Apache-2.0) is a Claude Code
plugin for drafting an SSP against an existing catalog. That is a
neighbouring problem, not the same one. Two of its scripts have designs worth
reusing for this repo's task of authoring a new Catalog/Profile from verbatim
document text: `extract-legacy-doc.sh`'s document-sectioning and
traceability scheme, and `validate-oscal-package.sh`'s validation-report
shape. The plugin is agent-only tooling with no installable or versioned
interface, so neither vendoring path fits. The logic is **ported as native
Python** instead (`normalizer.py`, `trestle_ops.py`), with Apache-2.0 §4
attribution headers noting origin and licence
(`docs/adr/0030-vendor-oscal-reference-content.md` §"Implementation note
(2026-09-24)"). The ADR records two rejected alternatives: vendoring the
plugin and shelling out to its scripts, and depending on it as a package,
which isn't possible because it isn't published as one. Full detail is
deferred to `specs/003-oscal-ai-conversion/research.md` R10, which is not a
source of this page.

## The `fedramp-automation` substitution

ADR-0030 originally named `GSA/fedramp-automation` as the FedRAMP submodule's
source. By the time GH #22 implemented it, that repo no longer existed on
GitHub — a confirmed 404, not a rename/redirect — with GSA apparently having
consolidated FedRAMP OSCAL content onto
[automate.fedramp.gov](https://automate.fedramp.gov), a documentation site
rather than a git-hosted source and so not submodule-able
(`docs/adr/0030-vendor-oscal-reference-content.md` §"Implementation note").
`third_party/fedramp-automation` is vendored from `GoComply/fedramp` instead:
an active open-source CLI for processing OSCAL-based FedRAMP SSPs that
bundles resolved LOW/MODERATE/HIGH baseline catalogs at `bundled/catalogs/`.
Unlike `oscal`/`oscal-content`, it is a processing tool rather than a pure
content mirror — no PRIVACY baseline, and while its own source is
CC0-licensed, the repo also vendors Go dependencies under their own
(non-CC0) licenses (`third_party/README.md` §"fedramp-automation"). The
revised ADR-0030 Decision no longer names the defunct upstream and points to
this implementation note for the actual source
(`docs/adr/0030-vendor-oscal-reference-content.md` §Decision).

## License compatibility

Apache-2.0 (`compliance-trestle`) and public domain/CC0 (`oscal`,
`oscal-content`) are compatible with this repo's AGPL-3.0 licensing — no
copyleft conflict, no NOTICE-file relicensing risk.
`fedramp-automation`/`GoComply-fedramp` is the one exception worth watching:
its own code is CC0, but it vendors Go dependencies under their own
non-CC0 licenses (`docs/adr/0030-vendor-oscal-reference-content.md`
§Decision; `third_party/README.md` §"fedramp-automation"). Its `LICENSE.md`
opens by saying the project "includes work in both the public domain and
dependencies that are not", but the checked-out file carries only the CC0
text and doesn't name those dependencies or their licences
(`third_party/fedramp-automation/LICENSE.md`). Checking them would mean
auditing the vendored Go module tree, which is not a source of this page.
Both NIST repositories state they are US-government works in the public
domain in the US, dedicated worldwide under CC0 1.0
(`third_party/oscal/LICENSE.md`; `third_party/oscal-content/LICENSE.md`).

## Sample data

`sample-data/oscal/` holds two illustrative PlantUML diagrams — not real
OSCAL content, just the resolution mechanics:

- `01-nist-baseline-resolution.puml` — one dimension: a NIST catalog imports
  and tailors into exactly one of the LOW/MODERATE/HIGH baseline profiles,
  optionally combined with the PRIVACY add-on profile, merged into a resolved
  catalog that components then implement against.
- `02-nist-fedramp-combined-resolution.puml` — two dimensions: a component's
  resolved catalog combines NIST's own HIGH baseline with FedRAMP's
  independently-tailored HIGH baseline.

ADR-0030 tracks pointing these (and future tests) at real catalog/profile
files from the vendored submodules as worked examples/fixtures as a
follow-up, not yet built as part of the vendoring decision itself
(`docs/adr/0030-vendor-oscal-reference-content.md` §Consequences).

## Consequences and open follow-ups

- CI must check out submodules (`actions/checkout` with `submodules: true`)
  or `third_party/*` — including the pre-existing `it4it` submodule —
  silently appears empty in CI (tracked as GH #21).
- No first-party build step depends on the vendored OSCAL/FedRAMP paths, so
  there is no `VENDORED_MODELS`-style wiring in `build.py`, unlike IT4IT.
- If a future need arises to fork and patch `compliance-trestle` rather than
  consume it as published, that supersedes ADR-0030 and needs its own ADR —
  the `third_party/` + `fork-sync` mechanism from ADR-0002 would then apply.
- The spec-alignment review of the OSCAL artefact-flow elements against the
  real `oscal` schema (GH #24) is enabled by this vendoring but tracked
  separately.
