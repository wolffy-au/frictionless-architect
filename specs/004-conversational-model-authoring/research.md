# Research: Conversational ArchiMate Model Authoring

Decisions only. Ids, fields and lifecycles are defined once, in [data-model.md](data-model.md).

| # | Decision | Why | Rejected |
|---|---|---|---|
| R1 | New package `platform/packages/modelling-specification`, built like `controls-compliance-catalog` (own `pyproject.toml`, path dep on `llm-provider-config`) | The model already names `art-pkg-modelling-specification` as subsystem 6's home (ADR-0011); ADR-0002's monorepo pattern is the established way to add subsystem code | `src/frictionless_architect/` (pre-migration flat layout, not where new subsystem code goes, `ARCHITECTURE.md` §8) |
| R2 | `architecture/model/build.py`'s YAML-load/merge/validate logic and `render_diagrams.py`'s view→PlantUML→SVG logic both move into the new package (`model_io.py`, `rendering.py`); root's `build.py`, `render_diagrams.py` and the skill's `validate.py` all become thin wrappers shelling into the platform venv (`poetry run --directory platform python -m modelling_specification.cli build\|render\|validate`) instead of each holding their own pyArchimate logic | The router needs this logic in-process anyway (R9's in-memory validate-before-write, R10's on-demand single-view render); porting it once and having every root entry point shell out gives one implementation instead of three, while keeping ADR-0001's boundary (root never imports a platform package — it only shells out, same as before, just applied to all three entry points) | Leaving `build.py`/`render_diagrams.py` as the implementation and having the package shell out to them instead (rejected — neither has an in-memory-validate-without-write or single-view-render mode today, and bolting those on as root CLI flags still leaves the model-loading code split across two homes); a second pyArchimate-based implementation inside the package (duplicates root's logic — the fork Assumption 1 forbids, just relocated) |
| R3 | `pyarchimate` and `rapidfuzz` become **runtime** dependencies of the new package only, not the root project | Root's copies stay dev/test-only (used by the skill and by test fixtures respectively); the running agent needs both at runtime, the skill still only needs `pyarchimate` | Promoting both at root (over-broadens root's dependency surface for code that doesn't run there) |
| R4 | NL-to-delta call goes through `llm-provider-config`/`litellm` (ADR-0034), component id `modelling-specification.conversational-authoring` | Established pattern already used by `controls-compliance-catalog`; no new credential path, no new provider-selection logic | A bespoke client in the new package (the exact duplication ADR-0034 exists to avoid) |
| R5 | Duplicate check (FR-005): `rapidfuzz.fuzz.token_sort_ratio`, threshold 80, on `name` and `description`; `type` counts as a match only on exact equality. ≥2 of the 3 similar flags the candidate | A concrete, testable number was needed to implement the Clarified "≥2 of 3" rule; `token_sort_ratio` tolerates word-order differences in architect-authored names/descriptions better than a plain ratio | Levenshtein ratio (more sensitive to word order than architects' naming style); embedding-similarity (new ML dependency, unjustified for short strings) |
| R6 | Interposed-element pattern check (FR-008) is config-driven: `conventions.yaml` lists `(source_type, relationship_type, target_type) → required intermediary type(s)` shapes, seeded from the `sw-neo4j → art-tech-neo4j-volume → store-akg` precedent already in the model | Makes the rule inspectable/editable data (Enterprise Convention Rule, per spec) rather than hardcoded Python; matches how the one real precedent in this model was resolved | Hardcoding the one known shape in Python (not configurable, fails "organisation-specific/editable" in the spec's Key Entity definition) |
| R7 | Override Decision Record is appended to the existing `store-ledger` (Forensic Audit Ledger) as a new `art-override-decision` artifact kind, not a new store | `store-ledger` is already defined as "append-only, immutable record of ... governed state transitions" — an override is exactly that; reuses existing ledger infrastructure instead of inventing parallel infrastructure (Principle I DRY) | A dedicated override-records table/file (duplicates ledger semantics for no gain) |
| R8 | Candidate Delta lives only in process memory, keyed by a session id the chat router issues; nothing is written to disk or a database until accepted | Matches Clarification 2 (session-scoped, discarded on interruption) exactly; avoids building a persistence/resume path the spec explicitly deferred | A durable drafts table (rejected in the spec's own "Rejected alternative" note) |
| R9 | Validation runs against an **in-memory merge** of the current YAML model plus the candidate delta (a `pyArchimate.Model` built via `model_io.py`, with the delta's elements/relationships added before any check runs); nothing is written to `architecture/model/` until validation passes or the architect overrides | FR-002/003 require validation **before** applying; `model_io.py` is the one load path (ported from `build.py` per R2) both the in-memory validate and the CLI `build` use | Writing speculatively then rolling back on failure (risks a partial write surviving a crash, and complicates the discard-on-interruption rule) |
| R10 | Live rendering is request/response, not a websocket/SSE channel: the chat endpoint's response says what changed; the UI calls a `GET` render endpoint (auto, right after apply, or on explicit request) which returns a freshly rendered SVG via `rendering.py`'s single-view path (ported from `render_diagrams.py` per R2) | FR-012/013 only require "no manual step," not a push channel; matches the existing visualiser's poll-based `/schema-payload`/`/status` pattern (ADR-0023-adjacent) — no new transport needed for an MVP | WebSocket/SSE push (adds a stateful connection and reconnect handling the spec's success criteria don't need) |
| R11 | Override rationale is an optional field; an override recorded without one is stored with `rationale: null`, never blocked | Edge case 7 is explicitly left as an open question in the spec (not a Clarification); blocking the override on a missing rationale would contradict FR-014's "the agent MUST record the override ... rather than discarding it" — recording something is safer than refusing to record anything. Revisit via an Enterprise Convention Rule if the architect wants rationale mandated later | Rejecting the override until a rationale is supplied (not supported by any FR; invents a new rejection path the spec doesn't describe) |
| R12 | Business-layer wiring (Assumption 6): new `vs-intent-to-model` ValueStream, `process-conversational-authoring` BusinessProcess, served by the existing `coa-executable-governance` course of action and `stk-architecture` stakeholder — same shape as the other four outcome streams | "Owned by a new ValueStream" was settled during specification (spec.md Assumption 6); this plan's job is only to assign concrete ids/wiring (Principle XI) following the existing 1:1 stream↔outcome, stream↔course-of-action pattern | Folding conversational authoring into `vs-governed-delivery`'s `vss-baseline` stage (reuses more, but contradicts the already-settled "new ValueStream" decision) |
