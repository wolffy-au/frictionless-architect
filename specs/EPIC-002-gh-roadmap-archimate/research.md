# Research: GitHub Roadmap as ArchiMate Implementation & Migration

Decisions only. Ids, relationships and the Deliverable rule are defined once, in
[data-model.md](data-model.md). Superseded designs (Gap-by-hierarchy, `gh-*` ids, milestone
inheritance) are in git history at `f593ea8`.

| # | Decision | Why | Rejected |
|---|---|---|---|
| R1 | Emit only Plateau, Deliverable and Work Package; Gaps, `plat-baseline` and Strategy stay hand-authored | A Gap is an architectural judgement GitHub cannot express; GitHub cannot tell an epic from a task | Gap-by-issue-hierarchy |
| R2 | No Work Package → Plateau link; it reaches the Plateau through a Deliverable. Legality was probed against `validate.py` | A direct edge is redundant under the derivation rule and hides which release delivered the work | WP → Plateau Realization (legal but dropped) |
| R3 | `build.py` gets `MODEL_LAYERS = [*VENDORED_MODELS, HERE / "gh-roadmap"]`; a missing dir is skipped | Same `det_id()`/`NS` pass as ADR-0029, no reconciliation step. Generated ids share a namespace with hand-authored `plat-*`, `del-*`, `wp-*` but differ in shape; `add_elements` errors on a duplicate | Separate build step |
| R4 | Type-prefixed ids with a number; retitling changes the id | Keeps the source system out of the model; stale hand-authored references fail loudly | `gh-*` ids |
| R5 | In scope only with the issue's own milestone; drafts and pre-releases skipped | Scope is a field test, and the author controls granularity | Inheriting from parent or descendants |
| R6 | Closed Work Package → first release published after `closedAt`, else unreleased | GitHub has no issue-to-release link; close time against publish time is the only signal | Last release before closure; a manual label |
| R7 | Dependencies from native `blockedBy`; out-of-scope ends dropped; cycles emitted as written | Triggering is legal between Work Packages and between Plateaus | — |
| R8 | `gh api --paginate` REST for milestones and releases; one paginated GraphQL query for issues (`closedAt`, `parent`, `blockedBy`); cap of 1000 issues (ten pages of 100): fail if `hasNextPage` is still true after the cap | One query avoids N+1; `gh` supplies auth; never import a partial set (FR-009) | `gh issue list --json` (no parent or dependency data) |
| R9 | Sorted output, `yaml.safe_dump` with fixed options, no timestamps; write `*.tmp` then `os.replace` after all three render | Byte-identical re-runs; a failed fetch leaves the layer untouched (FR-007, FR-009) | — |
| R10 | Text enters YAML only through `safe_dump`; `bfn-*`/`plat-*` tokens honoured on exact match only; no fuzzy matching | Fuzzy matching could invent a relationship (Principle VII); `_check_null_keys` stays as a backstop | Fuzzy name matching |
| R11 | Per-milestone views (`implementation_migration` viewpoint); the overview view picks elements up via `include_types`; diagrams regenerated by `render_diagrams.py` | `add_views` errors on a missing member, and members come from the same element set. Confirmed: the viewpoint admits Plateau, Deliverable, WorkPackage and Gap, and leaves relationships unrestricted | — |
| R12 | Same change retires `plat-runtime-mvp` and `plat-runtime-target` (replaced by the generated Plateaus), renames `gap-runtime-hosted` for `multi-user-collaboration`, and adds a `plat-baseline` → first-MVP Gap | FR-011. Milestone #2 `multi-user-collaboration` was created on GitHub 2026-10-04 | — |
| R13 | Inject `run_gh(args) -> str`; unit tests use recorded JSON; one integration test builds a fixture layer and asserts `validate.py` exits 0 | No network in tests. Cases follow the invariants in `data-model.md` | — |
| R14 | Keep the 1000-issue cap (ten pages); budget a full import at the cap to 2 minutes wall-clock (spec.md SC-007, GH #104) | Measured: this repo (~100 issues, one GraphQL page) ran in 4–6s over 4 `gh` calls, each 0.5–2s; a synthetic 1000-issue fixture computed and rendered the layer in under 2s with network mocked out. Ten sequential pages at the cap extrapolate to well under a minute; the 2-minute budget adds headroom for GitHub API slowness or rate-limit backoff, not for the cap being wrong | Raising the cap (not supported by the measurements — the bottleneck is `gh` call latency, not compute, and stays linear) |
