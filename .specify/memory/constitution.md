# SpecKit Constitution

## Detailed References (Deeper Detail)

This constitution is the root of the documentation tree. Every document below links back
here; consult it when you need deeper detail.

### Normative — how we build

- **`TECHNICAL.md`**: Implementation-level guidance, coding standards, process expectations,
  best practices, and preferred standards that dictate how all requirements (functional and
  non-functional) are implemented.
- **`NONFUNCTIONALS.md`**: Abstracted quality-attribute requirements — performance,
  reliability, security, and compliance — that define what the system must achieve.

### Architecture — what we are building

- **`docs/adr/`**: The decision log (MADR). The authoritative record of every load-bearing
  decision; its `README.md` is the index.
- **`architecture/model/`**: The canonical architecture model (graph-loadable YAML). Every
  ArchiMate and C4 diagram is generated from it.
- **`ARCHITECTURE.md`**: The narrative — repository topology, target state, migration
  sequence. Must agree with the ADR log and the model (Principle X).

### Requirements — why

- **`specs/<feature>/`**: Executable feature specs (spec → plan → tasks).
- **`PROJECT_SPECIFICATION.md`**: Historical business and domain requirements. Use it as
  input when deriving user stories, requirements, and acceptance criteria for new specs; do
  not edit it except to record historical context.

### Process — how we work

- **`AGENTS.md`**: Development guide for people and agents — toolchain, gates, conventions.
- **`CONTRIBUTING.md`**, **`RELEASE.md`**, **`SECURITY.md`**: Contribution, release, and
  vulnerability-reporting procedures.

### Derived — never a source

- **`wiki/`**: Regenerated by the `wiki-librarian` skill from the documents above. Never
  cite it as a source and never hand-edit its pages.

## Resolving Conflicts Between Documents

No document automatically wins a conflict. When two documents — or a document and the code
or model — disagree:

1. **Stop.** Do not pick a side and carry on building on it.
2. **Find the root cause**: which decision was made, where it was recorded, and which
   documents failed to follow it.
3. **Get a final answer** from the maintainer before changing anything.
4. **Fix every affected document** so they agree, and file or amend an ADR when the answer
   is load-bearing.

## Core Principles

### I. Code Quality (Excellence through Clarity)

Logic must be self-documenting, modular, and adhere to SOLID principles. We prioritize readability over cleverness. Every function must have a clear purpose and minimal side effects.

- **Rules**: No "magic numbers," use descriptive naming, keep functions under 30 lines where possible. For detailed guidance on code structure and naming, refer to `TECHNICAL.md`'s "Code Style" and "File Structure" sections.
- **Rationale**: Maintainability is the primary constraint for long-term project health. We adhere to the **DRY (Don't Repeat Yourself)** principle to minimize redundancy and improve consistency.

### II. Testing Standards (Verified Correctness)

Automated tests are non-negotiable. Every feature must include unit and integration tests. Test coverage MUST prioritize critical paths and edge cases. We follow the Red-Green-Refactor cycle, embracing **Test-Driven Development (TDD)** principles.

* **Rules**:
  * Overall line coverage MUST stay at or above **90%**, enforced by
    `scripts/pre_merge_checks.sh` (`--cov-fail-under=90`). Core business logic targets
    100%. Tests must be isolated and reproducible.
  * Implementation should begin by writing tests first, checking the tests fail, stubbing out the code, confirming the tests pass, and then beginning implementation.
  * For detailed testing practices and framework choices, see `TECHNICAL.md`'s "Patterns and Practices > Testing" section.
* **Rationale**: Tests provide the confidence to refactor and ensure regressions are caught early.

### III. User Experience Consistency (Unified Interface)

Interfaces MUST follow established patterns to ensure predictability. Whether CLI or GUI, the user's mental model MUST be respected. Error messages must be actionable and clear.

- **Rules**: Use consistent command structures for CLI; provide helpful error messages with resolution steps. For comprehensive guidance on API design principles that ensure consistency, refer to `TECHNICAL.md`.
- **Rationale**: Consistency reduces cognitive load and improves user trust and efficiency.

### IV. Performance Requirements (Efficiency by Design)

System responsiveness is a first-class citizen. Code must be optimized for resource efficiency. Any operation exceeding 200ms must be asynchronous or justified.

- **Rules**: Profile critical paths; avoid premature optimization but maintain O(n) awareness. Performance considerations are further detailed in `TECHNICAL.md`'s "Performance" section.
- **Rationale**: Performance is a feature; a slow system is a broken system for the user.

### V. Security Practices (Proactive Defense)

Security is paramount throughout the development lifecycle. We adhere to secure coding practices, referencing established guidelines such as **OWASP**, **CWE**, **CERT Secure Coding Standards**, etc.

- **Rules**: Never commit sensitive information; validate all user inputs; use environment variables for configuration. Detailed security guidelines are available in `TECHNICAL.md`'s "Security" section.
- **Rationale**: Protecting data and systems from threats is a fundamental responsibility.

### VI. State Management and Workflow Integrity (Predictable Evolution)

Logic must define clear lifecycles and state transitions for key entities to ensure predictable evolution and auditable workflows. Data integrity must be maintained through controlled state changes, preventing invalid transitions.

- **Rules**: Document entity lifecycles and state transition rules. Implement these rules rigorously. Refer to `TECHNICAL.md` for detailed patterns on implementing state management and workflow control.
- **Rationale**: Robust state management and enforced workflows enhance system predictability, reliability, audibility, and maintainability, crucial for governance and complex processes.

### VII. System Integrity & Accuracy (Faithful Outcomes)

Every outward behavior, calculation, and state transition must be accurate and reproducible. Architecture models in
particular must faithfully reflect the intended reality — every element, relationship, viewpoint, and derived metric
consistent, traceable, and free from silent corruption, because stakeholders make strategic decisions from them.

- **Rules**:
  - Definitions, constraints, derived data, and published results must pass validation checks before release. Any change that affects state or outputs must be traceable through logging or metadata that explains why it occurred.
  - For architecture models: schema definitions, property constraints, and derived metrics are validated before a
    change is accepted; changes to relationships or hierarchies trigger automated consistency checks so invalid
    configurations cannot propagate; change logs capture modelling decisions that affect semantics.
- **Rationale**: Confidence in the platform stems from predictable, trustworthy outcomes. Inaccuracies amplify over time
  and create cascading fixes, and decisions built on an inaccurate architecture map waste effort and risk deployments.

### VIII. Durability & Interoperability (Preserving Continuity)

Project artifacts, data, and integrations must survive upgrades and align with other systems without degrading intent or
context. Architectural knowledge spans releases, teams, and tooling surfaces, so the context behind decisions must never
be lost.

- **Rules**: Introducing or evolving a format, model, or integration requires documented migration/mapping paths for
  existing data and behaviors. Import/export routines (ArchiMate exchange format, CSV/JSON snapshots, plugin interfaces)
  must preserve semantics, metadata, and linked artifacts across environments. Automated checks should detect semantic
  drift after upgrades.
- **Rationale**: Losing context or breaking interoperability forces costly rewrites, chases away architects, and severs
  the institutional memory that gives historical decisions their value.

### IX. Cross-Platform Consistency (Universal Accessibility)

The product must deliver reliable, equivalent functionality across the platforms we support. Differences in environments (hardware, OS, display, accessibility) should not manifest as inconsistent behavior or data fidelity gaps.

- **Rules**: UI components, rendering paths, and performance expectations should be verified across platforms.
  Platform-specific integrations (file dialogs, clipboard handling, GPU rendering) must degrade gracefully and protect
  data integrity.
- **Rationale**: Consistent behavior keeps users productive and minimizes confusion when switching devices or sharing outputs.

### X. Decision Traceability & Documentation Integrity (One Source of Truth)

Every load-bearing decision is recorded once, and every document that describes the system follows it. A narrative that
contradicts a recorded decision is a defect, not a difference of opinion.

- **Rules**:
  - Any load-bearing choice gets an ADR under `docs/adr/`, created from `0000-adr-template.md`.
  - An Accepted ADR must be reflected in `ARCHITECTURE.md` and `architecture/model/` in the same PR. When that is not
    possible, open a tracking issue and mark the ADR **A\*** (accepted, not yet reflected) in the `docs/adr/README.md`
    index until it is.
  - Diagrams are generated from `architecture/model/`, never hand-edited. The `wiki/` is derived and never a source.
  - Conflicts between documents are resolved as set out in "Resolving Conflicts Between Documents".
- **Rationale**: Stale narrative documents mislead anyone who reads them as the current source of truth. Recording
  decisions once and making every other document follow them keeps the architecture explainable and auditable.

## Development Workflow

Our workflow is designed to ensure that every change is intentional and verified. It follows a sequence of:

1. **Specify** (`speckit-specify`): Define requirements and user stories in a feature spec.
2. **Plan** (`speckit-plan`): Research technical approaches and generate design artifacts.
3. **Record**: File or update an ADR for every load-bearing choice the plan makes (Principle X).
4. **Break down** (`speckit-tasks`): Map the plan to tasks and requirements.
5. **Implement** (`speckit-implement`): Execute tasks following the Red-Green-Refactor cycle.
6. **Verify**: Pass all quality gates before merging — `scripts/pre_commit_checks.sh` on
   every commit, `scripts/pre_merge_checks.sh` before merge.

For more on our patterns and practices, see `TECHNICAL.md`.

## Quality Gates

Before any feature is considered "Done," it must pass these gates:

* **Linting & Formatting**: `ruff`, `pyright`, `mypy`, and `pymarkdown` pass, as detailed in `TECHNICAL.md`.
* **Test Suite Pass**: All new and existing tests (pytest and behave) must pass without failure after the implementation
  of every user story, adhering to the standards in `TECHNICAL.md`.
* **Coverage**: Overall coverage at or above 90% (Principle II).
* **Commit Messages**: Every commit follows Conventional Commits, enforced by commitizen (ADR-0025).
* **Documentation & Decisions**: READMEs, specs, and inline comments are updated; load-bearing choices have an ADR;
  `ARCHITECTURE.md` and `architecture/model/` agree with the ADR log (Principle X).
* **Constitution Check**: Implementation must be reviewed against these core principles.

## Governance

This constitution is the supreme guide for SpecKit development.

- **Amendments**: Proposed via PR; requires explanation of why the change improves project governance.
- **Versioning**: Follows semantic versioning.
- **Principle identifiers**: Principle numbers are globally unique and never reused. Domain-specific principles are
  added here with the next free number, not in a separate document.
- **Compliance**: All contributors must adhere to these principles; deviations must be justified in the `plan.md` complexity tracking section.
